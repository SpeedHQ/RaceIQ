# Automatic iRacing IBT reconciliation: UI implementation plan

Status: proposed; not implemented or verified.

Shared boundary, policy, acceptance and E2E: [Reconciliation contract](iracing-ibt-reconciliation-contract.md). Decision: [ADR 0015](../adr/0015-automatic-iracing-ibt-reconciliation.md). Parallel implementation: [Backend plan](iracing-ibt-reconciliation-backend-plan.md).

## Scope and ownership

Expose unattended reconciliation honestly in the existing iRacing Connection card and affected session/replay surfaces. No upload workflow, file chooser, new enable preference, per-file confirmation or manual matching is required. Preserve incumbent layout, native capture connect/disconnect behavior and existing standalone IBT import. Do not redesign the application or make clients perform filesystem matching.

Owned files/components:
- `client/src/components/settings/connection/IRacingConnection.tsx`: existing capture query, connection state and local archive status.
- Existing Analyse/session replay source-status presentation and associated query consumers; extend the current source/provenance presentation, rather than render a separate duplicate track scene. Resolve the narrow presentation component before editing.
- Existing replay/compare query invalidations, shared API consumption and locale messages.
- Seeded sessions/analysis/compare Playwright assertions and narrowly scoped development fixtures.

Backend owner publishes shared schemas and owns production source matching, persistence, scene geometry policy, API operations and integrated E2E execution. UI may proceed in parallel with typed contract fixtures after boundary acceptance; development fixtures must not become production fallback data. Shared contract changes update both plans before dependent changes continue.

## Tasks and observable acceptance

1. **Automatic status in Connection — UI-01; RC-01/07.** Extend existing capture response consumption with contract reconciliation summary. Keep capture state and reconciliation state separate: savedFiles is archive activity, not proof a session was reconciled. Show durable counts for waiting, processing, reconciled and attention outcomes, with unambiguous labels. Existing Connect remains the opt-in; clearly explain that correct IBTs are discovered locally and processed after disk-file closure. Show disabled/unsupported discovery accurately without a new confirmation flow.
2. **Per-session coverage and limitations — UI-02; RC-03/04/06/07.** Consume per-session status for an open iRacing session/replay. Show measured coordinates from IBT versus lap-progress estimate, matched and usable-position counts against live frame count, and concise state/reason. Completed with partial coverage must say partial; no-file/writer-open/active-capture are waiting, not success or corruption. Ambiguous identity/conflicting supplement/missing source/corrupt file have distinct actionable explanations. Do not expose private paths or invent a manual matching action; repaired/new evidence retries automatically. Preserve existing live telemetry while supplementary data is unavailable.
   Consume the contract's [semantic replay wire extension](iracing-ibt-reconciliation-contract.md#semantic-replay-wire-extension) for source attribution, not guessed attribution from addedChannels. Required `supplementalProvenance` entries identify consumed IBT rows/components; empty arrays mean no supplemental attribution, not proof of live measurement. Preserve primary-source labels and show mixed per-wheel/array attribution honestly. RE-07a covers real HTTP-to-browser provenance, null/invalid observations and absence of private paths; UI-02/04, RC-03/04/07.
   Reference the contract's [non-GPS inventory](iracing-ibt-reconciliation-contract.md#non-gps-enrichment-inventory) when explaining addedChannels; distinguish measured source enrichment from new analysis availability. Do not advertise continuous tyre data from channel presence, conflate surface/carcass readings, or claim slip/suspension/braking analyses were added. RE-04b verifies actual additions and truthful existing source-status presentation; RC-03/04/07/08, UI-02/04.
3. **Reactive replay refresh — UI-03; RC-05/06/07/08.** Keep existing capture polling; poll per-session status while its relevant surface is open, including every session represented in comparison. Refetch on focus/reconnect and invalidate actual replay/compare/scene queries when the contract's replay-evidence epoch changes, including loss/corruption/restoration with unchanged attachment IDs. A status-only revision change must not rebuild telemetry. Reject replay responses older than an already observed epoch; do not present old supplemental values as current while refresh is pending or failed. Preserve usable primary telemetry, selected lap, playback position, camera/focus and session expansion. Never add a new WebSocket event contract or client matching loop. RE-08a covers open hot-cache transitions, duplicate notifications, disabled discovery and restart/reconnect recovery.
4. **Geometry truth and access — UI-04; RC-04/06/07.** Consume the selected lap's `reconciliation.geometry` from its semantic replay response under the shared [geometry safety policy](iracing-ibt-reconciliation-contract.md#geometry-safety). Match lap/evidence/reference/policy keys before showing an accepted overlay; never use a session-wide result or another lap's acceptance. Comparisons preserve each lap's own result. Render approximate accepted reference, unavailable reference or rejected fit; measured path survives reference rejection or pending revalidation. Do not imply geographic telemetry automatically georeferences SVG or enables measured live GPS/native tire trails. Preserve global auth/not-found handling. Make status/coverage available as text, not color/hover alone, with polite progress announcements and alert semantics for failures. Update all existing locales; inspect 390px/1440px and long translated reasons without overflow. RE-07a proves mixed-lap selection/comparison and stale response/reference/policy rejection.
5. **Production integration — UI-01–04; RC-01/03/04/05/06/07/08.** Integrate real capture/status/replay APIs, remove development fixtures from runtime paths, and contribute UI assertions to shared E2E scenarios. Coordinate one documentation/changelog update with backend owner, not a separate cosmetic ADR or duplicate release note.
6. **Durable workflow tracking — UI-05; RC-05/07/09.** Display server-projected workflow stage and persisted next-wake information using the shared nullable workflow field. Distinguish waiting/retrying from active processing without a browser-owned retry engine or fabricated progress percentage. Backend restart/reconnect restores the same execution and recorded stage; a new evidence-keyed execution is an update, not a second session. Null workflow metadata means not yet admitted, not completed. A durable-store service failure is an explicit status error while cached primary replay stays usable.
   Consume `reconciliation.store` independently of capture status: journal unavailability shows an explicit reconciliation error but leaves existing capture connect/disconnect usable. Handle the session endpoint's typed HTTP 503 without erasing cached primary replay. RE-09 covers this boundary.
   Worker execution is backend-only and requires no new browser operation. Worker restart preserves execution/stage display; bootstrap/channel failure uses the shared service-error boundary while capture controls and cached primary replay remain available. UI assertions in RE-10 cover recovery and no false completion; UI-03/05, RC-07/09/10.
   Consume the summary's worker lifecycle independently of journal readiness, and handle `reconciliation-worker-unavailable` HTTP 503 explicitly; absent ready acknowledgement must never be presented as running reconciliation. No browser worker controls are added.

## Edge cases and E2E mapping

| Case | Expected handling and proof |
| --- | --- |
| Enabled startup finds historical matching IBT; normal live run closes new IBT | No upload/confirmation; automatic counts and session provenance update. RE-01/02; UI-01/02. |
| Disabled capture or unsupported host | Existing opt-in/availability remains authoritative; no claim that discovery is running or completed. Previously published replay remains usable. RE-02; UI-01/02. |
| No file, writer still open, active capture | Waiting reason and unchanged primary replay; do not ask user to import or claim coordinates available. RE-04/05/06; UI-01/02. |
| Wrong/ambiguous identity, corrupt source, changed evidence | Display specific attention state; no guessed selection or successful attachment; automatic recovery reflected after input changes. RE-03/05; UI-01/02/03. |
| Partial coverage, missing heading, invalid GPS, bad fit | Display actual coverage and unavailable/rejected geometry; preserve measured path where valid and primary data everywhere. RE-04/07; UI-02/04. |
| Complete accepted lap and partial/rejected lap in one session; reference/policy changes | Read each selected lap's keyed HTTP geometry; invalidate obsolete fit keys, never promote rejection through another lap, retain measured path. RE-07a; UI-02/04. |
| Primary-only, supplemented, invalid and mixed-component values | Render attribution from required HTTP provenance arrays without relabeling primary values or exposing source paths; empty/missing observations do not fabricate provenance. RE-07a; UI-02/04. |
| Lost status/replay response, reconnect, publication while viewer is open | Existing cached primary data stays usable with warning; real refetch/revision invalidation restores enriched view without selection reset. RE-07; UI-03. |
| Attachment loss/corruption/restoration and export/import | Unchanged attachment IDs do not prevent epoch-driven refresh; open analyse/compare removes then restores only supplemental evidence, agrees with cold reads and survives reconnect. Primary replay remains usable; imported provenance is preserved. RE-08/08a; UI-02/03/04. |
| Mobile, keyboard, long locale, inaccessible session | Readable bounded UI and semantic status; existing access boundary applies, no private source leak. RE-02/07/08; UI-04. |
| Backend restart during activity, durable wait or retry; journal unavailable | Restore server-owned stage/wake state and execution identity without client restart commands or reset-to-zero assumptions; distinguish explicit service failure from successful completion. RE-09; UI-03/05. |
| Dedicated reconciliation worker crash/replacement or compiled bootstrap failure | Preserve primary replay/capture controls; show explicit reconciliation unavailability, then restore durable stage after worker recovery without creating a new session or claiming completion from a stale message. RE-10; UI-03/05. |

## Verification and completion dependency

Extend existing seeded Playwright sessions/analysis/compare suite against real HTTP backend, dedicated Bun reconciliation worker and SQL-backed durable Effect journal. UI owner supplies assertions for RE-01–10; backend integration owner executes shared matrix and records RC-01–10/UI-01–05 evidence. RE-09 proves backend-process recovery; RE-10 proves worker-only recovery and truthful status/capture behavior after worker bootstrap/channel failure. Verify actual measured scene, not only JSON/status screenshots. Development mocks never satisfy integration acceptance.

After implementation run changed-path browser scenarios, accessibility/responsive checks and applicable existing project gates. Include real Windows native collection → automatic matching → browser replay evidence before acceptance; unavailable Windows/simulator access remains a blocker. Record unexecuted checks explicitly. No tests, implementation, commits or checkpoints are performed for this planning-only request.
