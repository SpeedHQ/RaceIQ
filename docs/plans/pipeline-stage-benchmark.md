# Matched Bun/Rust pipeline-stage benchmark

ADR: [Isolate processing stages](../adr/0004-pipeline-stage-benchmark.md).

## Requirements

Mirror the purposeful Bun benchmark: separately measure raw-frame parsing and processing of already-parsed packets. Use production code, the same source frames, stateful parsers, and release Rust. Load/decode fixtures, transport data, prepare state, and construct packets outside the relevant timers. No UDP, disk writes, database persistence, or recording shutdown in measured work. Preserve existing benchmarks; disk-import implementation remains paused.

## Implementation

- Add a dedicated Bun runner using the six existing canonical recorder fixtures, bounded to 10,000 source frames per game by default. The FM fixture begins active telemetry at index 5,218, so a 5,000-frame prefix is empty for processing. Preserve context/segment markers and available host timestamps.
- Send exactly those decoded records to a dedicated native benchmark entry point. Decode request/base64 outside timers; return per-stage samples after processing.
- Parse stage: production full-presentation parsers, freshly prepared state per trial, source-order input; consume outputs and report accepted packet counts. Exclude capture decompression/framing and suppress pipeline console logging as in the original benchmark.
- Processing stage: prepare packets before timing; use Bun LiveTelemetryPipeline with null DB/WebSocket/recorder adapters and disabled history/dev state, Rust production Detector reference ingress. Bound detector retention by fresh state per 500-packet chunk; include each chunk's incomplete/final detector flush inside timing. Segment boundaries also terminate chunks. Construct state and clone mutable Bun packets before timing.
- One warmup and 20 measured trials per stage/game by default. Report median elapsed time, ns/source frame for parse, ns/accepted packet for processing, fixture/workload hashes, counts, engine/build and scope. Explicitly distinguish Bun pipeline orchestration from Rust detector/event processing; do not claim full feature or semantic parity.
- Expose engine, game, trials, frame-limit and output options; default comparison runs engines sequentially. Fail empty workloads, native errors and invalid CLI values.
- Report code-only memory separately from timing in fresh per-game/engine processes. Load/decode fixtures before parse-memory baselines; prepare and clone full input packets before processing-memory baselines. Include parser/detector/pipeline state creation and work in each allocation window, but exclude loaded input, transport/base64/IPC and report construction. Use a feature-gated Rust allocator instrumented release binary for exact peak additional live requested Rust allocation bytes. Bun uses post-GC live-heap growth at bounded frame/chunk boundaries, labeled a sampled estimate: ordinary Bun heap counters remain stale between collections. Report parse and processing peaks/retention separately in JSON and terminal output. Do not present whole-process RSS as code-only memory or imply Rust allocation and Bun heap metrics are identical. Keep instrumentation out of throughput and normal production builds.
- Headline memory report compares median end-of-stage retained growth with parser/pipeline state alive and transient returned outputs released. Show Rust allocation peaks and Bun sampled post-GC maxima only in a separate diagnostic table with engine-specific labels. Preserve fixture/prepared-input exclusions and timing boundaries; version the changed retention semantics. Verify all six fixtures, reporting/disabled modes, state lifetime and schema/count consistency. Do not imply allocator equivalence or optimize production detectors merely to lower reported numbers.
- Clean lifecycle: each trial starts with fresh state; completed chunk state is released before processing the next chunk. Retain only the final chunk's state at the end-of-stage memory boundary, never the sum of all finished chunk buffers. Apply equally to Rust and Bun while preserving prepared-input exclusions, construction outside timing, packet/event counts and per-chunk flush behavior. Version this changed memory lifecycle and verify repeated trials across all six fixtures plus bounded state retention.
- Investigate the observed Rust parsing slowdown without changing production parsers: use a release-only diagnostic probe to separate full-presentation construction/destruction from compact detector-facing parsing. Preserve the original full-presentation benchmark contract and distinguish measured causes from hypotheses.

## Acceptance

Run actual runner against all six fixtures using release native binary; observe nonzero consumed packets and repeatable per-engine counts across trials. Show both stage distributions and disclose packet-count differences. Native build/check and backend typecheck pass. Exercise option/error boundaries. Update benchmark usage and changelog after smoke proof. No commits requested.
Code-only profiles must complete for all six canonical fixtures and both engines without overlapping throughput timing. Source/workload hashes and accepted/processed counts must match throughput inputs. Exercise fixture exclusion with held large fixture-like buffers allocated before baselines, and detect allocations created inside windows; failures must not become zero-valued samples. Disclose GC, sampling, native/C allocation and allocator-overhead limits. Replace old RSS labels/schema rather than keeping ambiguous aliases.
