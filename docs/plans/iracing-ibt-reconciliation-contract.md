# Automatic iRacing IBT reconciliation contract

Status: proposed; planning only. No implementation or runtime verification is claimed.

Plans: [Backend](iracing-ibt-reconciliation-backend-plan.md), [UI](iracing-ibt-reconciliation-ui-plan.md). Decision: [ADR 0015](../adr/0015-automatic-iracing-ibt-reconciliation.md).

## Outcome and existing contracts

Automatically find the correct local IBT recordings for existing live-recorded iRacing sessions, retain both sources, and enrich historical replay with measured geographic positions without importing duplicate sessions or losing live-only competitor/context data. Discovery and matching need no upload, file picker, or per-file confirmation. Reconciliation becomes available after iRacing closes its disk recording, not as exact live GPS.

Authoritative existing boundaries:
- [Adapter](../reference/adapters/iracing.md): live source frames retain native values and changing SessionInfo; normal IBT import retains original bytes.
- [Native collection](../../server/games/README.md): existing persisted Connect opt-in, Known Documents resolution, logging ownership, exclusive closed-file probe, immutable hash-named archives. Extend its historical-discovery limitation explicitly; do not silently bypass opt-in.
- [Track geometry](../../shared/racing/tracks/README.md): measured poses are distinct from native XYZ, reference geometry alone is fitted, missing/stale GPS remains unavailable.
- `apps/backend/src/runtime/iracing-capture.ts`, `packages/game-iracing/src/disk-logging.ts`: current collector and platform integration.
- `server/telemetry/replay.ts:46–113,152–241`: existing identity is native session UID + SessionTick + rounded SessionTime milliseconds. Do not align by packet index.
- `server/db/telemetry-replay-storage.ts`: existing lap/member identities and replay caches must remain valid and revision-aware.

Scope excludes fabricated live coordinates, moving/deleting native originals, whole-disk searches, auto-importing unrelated IBTs, modifying lap timing/validity/classification, racing-result reconciliation, and publishing derived poses as native telemetry. Existing standalone IBT import remains available and unchanged.

## Discovery, matching, and source precedence

1. Reuse the existing persisted iRacing capture opt-in. While enabled, resolve current user's Windows Known Documents `iRacing/telemetry` (including redirection), scan regular `.ibt` files there and owned archive files. Do not traverse unrelated directories, symlinks/reparse-point targets, or arbitrary client paths. No new permission setting is enabled automatically. Unsupported hosts report unavailable; the Windows backend must have access to the simulator user's files.
2. Extend startup discovery to historical files, but only archive/reconcile files positively matched to an existing owned live capture. Inventory headers incrementally, persist file generation/signature and outcomes, and rescan changed files rather than rehashing every file on every tick. Existing in-window archival continues. Native originals remain untouched. Recheck file generation and exclusive closed-file status before/after copy, hash owned staged bytes, then publish atomically without replacement. A paused writer is not complete.
3. Match each IBT session segment, not its filename: non-placeholder native SessionID, SubSessionID, SessionNum, exact native track/layout ID, car ID and player driver/car identity from retained source metadata must agree. Resolve player identity from SessionInfo driver metadata, including UserID when available; driverCarIdx alone is not globally unique. Offline/test sessions with zero IDs require the same car/driver/layout plus a unique exact overlapping native tick/time sequence; otherwise report insufficient identity, never guess from wall clock or lap number.
4. For every segment, require at least 60 distinct exact common `(session UID, SessionTick, round(SessionTime * 1000))` keys spanning at least one second with consistent native lap progress (absolute LapDistPct difference <= 0.001 for each compared valid pair). These are matching thresholds, not interpolation permissions. Duplicate or reset tick/time identities cannot cross segment boundaries. Missing identity, incompatible progress, multiple non-equivalent candidate captures, or driver swap identity uncertainty yields an explicit unresolved outcome. Do not choose the nearest filename/time or first candidate.
5. One IBT may cover several live sessions; one live session may need several IBTs from separate car entries. Build per-segment/per-range attachments. Byte-identical duplicate files share one archive identity. Overlapping attachments must have identical supplementary values for the same exact identity/channel or the new conflicting attachment is rejected; previously committed data remains intact. Disjoint attachments extend coverage atomically.
6. Keep live capture bytes, frame grid, native values, metadata timeline, lap/session IDs, offsets, notes, ownership and all user decisions unchanged. IBT supplements channels absent from the live source's variable dictionary for that segment. Never replace an existing live channel, including invalid/stale samples, with an IBT value. Retain the complete IBT for provenance and original-cadence access; do not discard its extra rows merely because the live grid has gaps.
7. Publish supplementary values only on exact unambiguous common keys. No nearest-row matching, resampling, interpolation, extrapolation, or carrying GPS through gaps. Missing/duplicate/conflicting rows remain unavailable. Position validity/freshness remains governed by the semantic resolver and ScenePlacement; retain `(0,0)`, invalid values, and missing heading as gaps, not fabricated zero coordinates. Report both matched-row coverage and usable-position coverage.
8. Store immutable owned IBT references, digest, source generation, matching version, range index and source/result revisions in durable attachment metadata. Expose per-value IBT provenance without replacing the primary live raw reference or falsely attributing GPS to live SDK. Reconciliation completion means source reconciliation completed; geometry acceptance is a separate state.

## Publication and state transitions

Use Effect 4.0.4 durable workflows, not an in-memory queue or a hand-built job-state machine, to own reconciliation execution and stage tracking. Run the reconciler and its durable Effect runtime inside one dedicated Bun-hosted `Worker`, supervised by the backend; never run reconciliation activities on the main event loop. Reuse existing parent-owned maintenance/write admission for domain side effects. Parse each changed IBT once per durable indexing activity; persist compact row/range indexes for selected-lap reads, not a JSON copy of every row.

States per existing live session: `waiting-for-file`, `waiting-for-close`, `pending`, `running`, `completed`, `limited`, `failed`; these are persisted projections of durable workflow progress and domain outcomes, not a second scheduler. Active live captures defer publication until their relevant source windows are finalized. No matching file stays waiting; absent disk logging explicitly explains that no coordinates can be recovered. Missing identity/ambiguity/no usable supplementary evidence is limited; corrupt bytes/I/O failure is failed. Changed evidence or processor version starts a new evidence-keyed execution automatically; unchanged limited/failed input does not spin. Interrupted work resumes the same durable execution from recorded activity results, rather than resetting every running session to pending and replaying the whole pipeline. Disconnect ends new external discovery under existing ownership rules; already accepted durable work can finish. Re-enabling resumes catch-up without importing unrelated sessions.

Archive publication precedes a short transaction that checks capture existence, finalization, ownership, source revision and attachment baseline, and commits all range attachments, reconciliation revision/status and derived invalidation together. Stale attempts discard computation and requeue current evidence; deleted sessions cannot be recreated. Crash after archive publication but before DB commit leaves recoverable unreferenced owned bytes, not visible partial reconciliation. Retention/relocation/deletion/export protect referenced attachments and never unlink native originals. Losing an attachment later reports unavailable supplementary data, preserves live replay, and schedules recovery if a matching original remains.

Replay caches, prepared comparisons, scene pose/geometry caches, and persistent derived artifacts that consume enriched semantic channels include the reconciliation revision. Unaffected primary timing/classification/results do not rebuild merely because GPS was attached. Existing read APIs fetch the enriched semantic replay; attachment-specific provenance is added to existing diagnostics with `sourceKind: "ibt-supplement"`, `attachmentId: string`, `sourceDigest: string`, `sourceRow: nonnegative integer`, and `reconciliationRevision: nonnegative integer` for supplementary values. Disk paths are not exposed through new public fields.

## Durable Effect execution contract

Use the installed Effect 4.0.4 `effect/workflow` APIs (`Workflow`, `Activity`, `DurableDeferred`, `DurableClock`) with `effect/cluster` `ClusterWorkflowEngine` and `SingleRunner` SQL-backed message/runner storage. Their installed source exports were inspected during planning; these APIs are unstable. Do not use `WorkflowEngine`'s in-memory layer in production or substitute the unrelated Cloudflare-only `@durable-effect/workflow` package. Validate the exact SQL driver/adapter against Effect 4.0.4 and Bun/Windows in the first backend implementation task; do not silently upgrade core Effect or downgrade to an in-memory engine if compatibility fails.

Store the durable engine journal in an owned SQLite file at `DATA_DIR/iracing-reconciliation-workflows.sqlite`, separate from the application domain database. Provision its compatible Effect `SqlClient`, migrations, SQL-backed runner storage and single-runner layer before discovery admits work. Keep one runner per backend/data directory; do not enable distributed runners or introduce a remote service. Journal writes use the journal connection; all application-domain mutations still use existing application write admission. Startup/readiness failure of the durable store prevents new reconciliation without disabling primary live capture or capture connect/disconnect. Capture responses report journal unavailability explicitly; reconciliation-only detail reads return the service error defined below.

The existing [recording maintenance guide](../contributing/scheduled-recording-maintenance.md) explicitly describes non-durable in-memory jobs. Reuse its reservation → maintenance lock → write permit → transaction order, Promise/Effect facade rules, protected non-cancellable I/O settlement and shutdown discipline; do not claim its scheduler already provides durable execution or migrate unrelated storage jobs. The durable Effect runtime lives inside the dedicated Bun worker and is scoped to that worker's backend-owned lifecycle, not a request, browser or detached fiber. All reconciliation archive/hash/index/match/fit preparation and workflow execution occurs there; the main thread only supervises, routes bounded control/status messages and performs admitted native SQL operations.

### Execution identity and activities

- Discovery inventories file generations durably, and records an outbox intent before acknowledging acceptance. Archive-publication and live-finalization events also create durable intents. An Effect dispatcher redelivers unacknowledged intents idempotently; losing an in-memory notification cannot strand work.
- A file-processing workflow key includes canonical inventory identity, file generation and processing version. It waits for closure, publishes/verifies immutable archived bytes, and produces an immutable native segment/range index. Deduplicated content can reuse a verified index; retries must recheck file generation and integrity, not trust a stale successful probe.
- A session-reconciliation workflow key includes owned session/capture identity, live source revision, a digest of the sorted candidate evidence set, prior attachment baseline and matching/policy version. Duplicate events execute/poll the same execution ID. Changed inputs create a new execution; obsolete executions cannot publish through current revision fences.
- Named, schema-serialized activities cover `archive`, `index`, `match`, `publish`, and `refresh`. Store compact identities, owned artifact references and result manifests in activity results, not entire telemetry, file handles, DB connections or mutable service objects. Completed deterministic indexing/matching results survive process restart; source-dependent commit checks always run in the publication transaction.
- `DurableDeferred` completions and durable clock wakeups handle file-close/finalization waiting and delayed retry without retaining an active loop or using process-local `setTimeout` as the durable record. Discovery rescans repair missed external notifications and complete the same durable wait idempotently. Persist waiting reason and next wake time for status projection.
- Retry only typed transient I/O/temporary availability failures with at most three retries at 1 s, 5 s and 30 s, using durable wakeups. Writer-open/no-file/active-capture are suspended waiting conditions, not failed retry attempts. Invalid identity, ambiguity, corrupt bytes or incompatible source is a terminal limited/failed result for that input; source change/version change creates new evidence-keyed work. Defects and interruption are never converted into successful empty attachments.

### Side effects, recovery, and tracking

Durable activity replay is at-least-once around external side effects, not a blanket exactly-once guarantee. Archive publication uses immutable digest identities and verification; index outputs use owned immutable references. The domain publication transaction records the execution/activity idempotency key with its attachment revision and durable refresh outbox. A retry after DB commit but before workflow-result persistence returns the existing committed result, without inserting duplicate attachments or incrementing reconciliationRevision again. Refresh delivery is idempotent and recoverable after a missed response or process death. Engine journal and domain DB are separate transactions; this outbox and idempotent publication protocol bridges them explicitly.

Workflow progress updates its domain read projection through revision-fenced activities; reads do not decode captures or advance workflows. A crash between engine progress and projection update is repaired from the engine's recorded result before status can claim completed. `completed` requires a committed attachment result and durable refresh intent; cache refresh may be retried safely, and reconnect/cold reads use reconciliationRevision. Retain terminal journal results at least until all domain/outbox references are settled; cleanup cannot remove a live dependency. Domain deletion tombstones and revision checks prevent replayed activities from resurrecting deleted sessions. Back up/relocate the journal with the owned data directory; exported sessions carry attachment provenance, not active runner messages.

Shutdown stops discovery/admission, drains or suspends owned executions at safe activity boundaries, awaits already-started Promise/worker I/O and domain transactions, then disposes the Effect runner and journal connection before database shutdown. Never release a maintenance/write lease while underlying I/O is still executing. Restart reopens the same journal, restores durable waits/timers and resumes executions without rerunning successful activities; authoritative domain checks still reject obsolete work.

### Bun worker ownership and bridge

Use the repository's Bun-hosted `node:worker_threads` `Worker` pattern in `apps/backend/src/runtime/startup-worker.ts`, including development and compiled entry-point resolution. Add a dedicated reconciliation supervisor, worker entry point and shared message schema beside that runtime. Do not reuse the startup/dashboard worker or create one worker per file/session. Keep the existing capture manager's SDK command/observation ownership; it sends durable discovery/finalization intents, not telemetry arrays, to the reconciliation worker.

| Owner | Responsibilities |
| --- | --- |
| Main backend | Spawn/supervise exactly one reconciliation worker; capture opt-in/SDK control and notifications; durable domain outbox acceptance; maintain parent-owned storage/maintenance/write authorities and native SQL transaction handles; expose status projections; deliver cache invalidations after committed publication. |
| Dedicated Bun worker | Own the scoped durable Effect engine/runner, durable dispatch/waits/retries and all reconciliation activities; scan/index candidate evidence in bounded batches, hash/archive, decode/match and prepare reference-fit results; read committed domain snapshots; request admitted domain publication and own journal SQL operations through the parent bridge. |
| Parent SQL bridge | Reuse `server/db/worker-sql.ts` and write-coordination lease semantics for application writes; maintain an isolated journal SQL host/connection and journal admission authority for engine storage. Parent owns native transaction handles for both databases; worker-side Effect SqlClient uses the journal bridge, not an independent application writer. Journal admission never acquires the application write permit. |

Use versioned structured-cloneable control envelopes with worker-generation and request IDs. Parent controls are `initialize`, `wake` and `stop`; worker replies are `ready`, `accepted`, `publication`, `error` and `stopped`, alongside the existing lease/SQL request-response protocol. Wake carries durable intent IDs; accepted means engine submission was durably recorded, not merely received. Stop acknowledges only after activity I/O/finalizers and runtime disposal settle. Publication carries session ID, execution ID and committed reconciliationRevision; parent ignores obsolete-generation messages and verifies current committed revision before invalidation. Persisted outboxes, not worker messages, are recovery authority. Bound in-flight controls; leave excess work durable in the outbox. Never structured-clone full telemetry or share native connection/transaction objects.

On worker error/channel loss, stop admitting messages for that generation, await actual worker exit, drain submitted parent SQL, and roll back/close its uncommitted domain and journal transactions before releasing leases or opening a replacement runner. A single supervisor may restart only after cleanup settles; resume the same journal/execution identities. Startup failure or repeated worker failure remains an explicit reconciliation service failure, never an inline fallback. Graceful shutdown sends stop and awaits stopped plus exit/bridge drain; forced termination is failure-test coverage, not normal shutdown. Include the worker entry point in compiled Bun artifacts and verify it runs in both dev and compiled Windows application paths.



## UI/backend boundary

Extend existing authenticated, feature-gated `GET /api/iracing/capture` and `PUT /api/iracing/capture` responses with required `reconciliation: ReconciliationSummary`; preserve existing top-level fields and PUT body `{ connected: boolean }`. No new action is required to reconcile. Add authenticated `GET /api/iracing/reconciliation/sessions/:sessionId` for per-session details using existing session ownership/access rules. Invalid IDs return 400; inaccessible/missing/non-iRacing sessions return existing not-found behavior. Unsupported discovery is a successful status response, not a false completed result. Unexpected server failures retain the existing error boundary.

If the workflow journal is unavailable, capture GET/PUT retain their existing capture behavior and include `reconciliation.store = "unavailable"`; summary counters remain the last durable domain projection, not proof of a healthy workflow. The session reconciliation endpoint returns HTTP 503 with `{ code: "reconciliation-store-unavailable", error: "Reconciliation workflow storage is unavailable" }`. This error must not disable capture disconnect or erase cached live telemetry. Unsupported platforms are distinguished by `supported = false`, not journal corruption.

Report worker lifecycle independently through `reconciliation.worker`: `starting`, `ready`, `unavailable` or `stopping`. Disabled/unsupported execution reports `unavailable`; existing supported/enabled flags explain why. No ready acknowledgement means no claim that execution is running. If journal readiness is established but worker bootstrap/channel fails, the session endpoint returns HTTP 503 with `{ code: "reconciliation-worker-unavailable", error: "Reconciliation worker is unavailable" }`; capture GET/PUT still work and show the worker state. During starting/stopping, detail reads may serve the last durable projection but cannot claim an active worker. The UI uses these states without exposing worker handles or creating a new start/restart control.

```ts
type ReconciliationState = "waiting-for-file" | "waiting-for-close" | "pending" | "running" | "completed" | "limited" | "failed";
type ReconciliationReason = "no-file" | "writer-open" | "active-capture" | "insufficient-identity" | "ambiguous-match" | "conflicting-supplement" | "missing-channel" | "no-common-frames" | "invalid-position" | "source-missing" | "corrupt-file" | "io-error";
interface ReconciliationSummary {
  supported: boolean;
  enabled: boolean; // existing capture opt-in, not a separate preference
  store: "ready" | "unavailable"; // durable journal readiness, independent of capture connection
  worker: "starting" | "ready" | "unavailable" | "stopping"; // parent-supervised executor readiness
  revision: number; // durable monotonically increasing status revision
  counts: Record<ReconciliationState, number>; // owned live iRacing sessions; each counted once
}
interface SessionReconciliation {
  sessionId: number;
  revision: number; // status revision, distinct from publication identity
  reconciliationRevision: number; // increments only when published attachments change
  state: ReconciliationState;
  reason: ReconciliationReason | null;
  workflow: { executionId: string; stage: "archive" | "index" | "match" | "publish" | "refresh"; nextWakeAt: number | null } | null;
  attachmentIds: string[]; // stable opaque IDs, ordered lexicographically
  liveFrameCount: number;
  matchedFrameCount: number; // distinct live frames with an attached exact match
  usablePositionFrameCount: number; // valid Lat/Lon and YawNorth, <= matchedFrameCount
  addedChannels: string[]; // native names, unique, lexicographically ordered
  geometry: { state: "unavailable" | "approximate" | "rejected"; reason: "no-position" | "insufficient-coverage" | "poor-fit" | "missing-reference" | null };
}
```

All numeric counts/revisions are finite nonnegative safe integers; `usablePositionFrameCount <= matchedFrameCount <= liveFrameCount`. Required nullable fields serialize as null, not omitted. Empty attachment/channel arrays mean none, not pending success. No pagination is needed for fixed summary/session endpoints. Existing capture polling remains authoritative; no new socket envelope. UI refetches per-session details while open, on focus/reconnect, and invalidates affected replay/compare queries when reconciliationRevision changes. A status revision alone does not imply new telemetry.

Representative session response: `{ "sessionId": 42, "revision": 8, "reconciliationRevision": 1, "state": "completed", "reason": null, "workflow": { "executionId": "opaque-durable-execution-id", "stage": "refresh", "nextWakeAt": null }, "attachmentIds": ["opaque-ibt-range-id"], "liveFrameCount": 6000, "matchedFrameCount": 5400, "usablePositionFrameCount": 5350, "addedChannels": ["Alt", "Lat", "Lon"], "geometry": { "state": "approximate", "reason": null } }`. Numbers are illustrative, not measured fixture results. Partial coverage is explicitly displayed; completed does not mean every frame has GPS. `workflow` is null before admission; otherwise it identifies the current or latest execution and its last entered stage. `nextWakeAt` is nullable Unix epoch milliseconds for a persisted scheduled wake, never a client countdown authority.

## Geometry safety

Keep measured east/north/altitude positions unchanged. Reuse ScenePlacement's reference-only fitting; never snap or scale the measured path. For display acceptance, validate using lap-fraction-corresponding samples from a complete lap: at least 90 of 100 equal lap-fraction bins represented, median residual <= 5 m and p95 <= 15 m after fitting. These conservative proposed limits belong here as versioned policy, not duplicated in clients. Insufficient coverage or a failed fit hides the reference overlay with an explicit reason while retaining measured trajectory. Validate transform orientation against forward lap progress; applying one transform to outline, edges, labels, pit lanes and sections is mandatory. Never promote an SVG fit to surveyed/native geometry or reuse it as exact live GPS. Persisted global track calibration is outside this change.
