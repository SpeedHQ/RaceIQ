# RaceIQ Online UI implementation plan

Status: client implementation delivered; presentation and real local RPC failure paths verified on 2026-10-12. Authenticated service/privacy acceptance remains blocked by the backend/service gates below. The shared [UI/backend contract](raceiq-online-contract.md) remains authoritative for DTOs, actions, errors, account epochs, polling, query keys, and local route mapping; no contract changes were made. The [backend and product plan](raceiq-live-service.md) owns backend implementation prerequisites and server-side guarantees. Decision context: [ADR 0011](../adr/0011-raceiq-live-service.md).

## Goal and boundaries

Implement optional RaceIQ Online surfaces using incumbent UI composition and styles: a skippable onboarding choice/connection flow, a minimal dedicated Online settings section, and per-track Community Laps boards. Preserve offline-first behavior and all existing local/community features. No redesign or separate account application.

UI ownership: `client/src/components/onboarding/OnboardingModal.tsx`, onboarding steps (including `steps/CommunityStep.tsx`), settings navigation and `Settings.tsx` plus Online section component(s), `client/src/components/track/TrackDetail.tsx`, `detail/` and `CommunityLeaderboard.tsx`, proposed `client/src/hooks/raceiq-online.ts` and `client/src/lib/raceiq-online.ts`, and client message sources for every supported locale. Reuse `client/src/hooks/settings.ts`, `track-queries.ts`, `query-keys.ts`, existing Paraglide messages, and established component/style/accessibility patterns; adapt only where required by contract. Backend owns proposed `shared/integrations/raceiq-online.ts` and exports, Hono routes/AppType composition in `apps/backend`, OAuth/callback/token handling, policy/preferences enforcement, upload queue/sanitization, and leaderboard service/cache. UI must not edit or independently redefine these shared/backend interfaces.

## Prerequisite and parallel implementation

The proposed contract is a planning boundary, not an implemented API. UI presentation can proceed against the exact `RaceIqOnlinePort` and contract DTOs using deterministic fixture-only scenarios in existing test/preview conventions. Do not add runtime mocks, `any`, guessed endpoint types, or raw `fetch` to bypass missing route types. Production adapter is gated only on backend landing/exporting real Hono routes and a usable exported `AppType`; then implement the adapter through existing `client/src/lib/rpc.ts` Hono RPC conventions. Do not invent placeholders or claim integration complete until real routes are wired. No SDK, auth secrets, uploads, or server policy enforcement belong in UI.

Backend/service limits remain real limitations: target SDK is `@speedhq/live-client@0.1.5`; deployed policy endpoint previously returned HTTP 502. Desktop auth/callback, policy availability/disclosures, canonical eligibility, safe F1 recording sanitization, idempotency, and other open service questions remain unresolved in the backend plan. UI must represent unavailable/error states truthfully; never imply these uncertainties are solved.

## Onboarding

Welcome retains its visualization and language selector, with Get Started in the modal footer. The next named step presents keyboard-accessible radio cards for RaceIQ Online and offline use. Online copy introduces community competition and the community's fastest laps; offline copy explains account-free local recording and analysis. Back and a single dynamic Continue action live in the footer. Continue is disabled until a card is selected, then becomes Continue with Discord (with Discord icon) or Continue offline. Selecting a card alone makes no Online request and never starts authentication. This is independent of the existing Community choice (`CommunityStep.tsx` remains about existing community functionality). Offline continues ordinary setup with zero Online requests. Discord opens authentication, followed by permissions only after backend-confirmed sign-in. Auth Back cancels pending sign-in, clears the selection, and returns to the choice step; offline Profile Back returns there with the offline selection retained. Named steps and a validated session-scoped resume record preserve authentication/permission progress across remounts. Ordinary setup remains intact; there is no duplicate Online step at the end.

After successful authentication, show current authoritative Terms and Privacy links and concise disclosures before permission submission: public participation means eligible recording upload for validation and possible public leaderboard display; private means no upload and no cloud validation; optional setup attachment is separately controlled and off by default; every uploaded F1 recording has embedded setup telemetry stripped regardless of attachment choice; local recordings remain unchanged. Explain public/setup settings remain changeable later. Do not hardcode policy URLs or assert unconfirmed data-retention/service claims.

Initialize both public sharing and setup attachment drafts off. Sign-in authenticates identity only and submits no consent or preferences. The permissions step requires explicit current-policy and choice confirmation, accepts those versions, then submits the complete preference pair only after acceptance succeeds. Continue ordinary setup only after confirmed preference persistence. Policy unavailable/changed blocks permission submission, not authentication. Cancellation or switching offline invalidates a pending auth flow before advancing; failures remain visible and retryable.

For Online onboarding, the name input starts empty and uses the connected account's confirmed display name as its placeholder. This is the Discord-derived name on first sign-in. Leaving it blank keeps the current name without a profile request; entering an override patches only the cloud `displayName` field, waits for service confirmation, then stores the confirmed name locally before navigation. The app does not modify Discord directly. Explain that the chosen name is publicly shown on the leaderboard. Show pending/error feedback; failed saves do not advance. Validate nonempty overrides as 1–80 Unicode characters without controls, and prevent stale-account responses from confirming another account's name. Offline onboarding retains its local-only optional name.

Represent connect pending/signing-in, external authorization open failure, user cancellation, callback pending, success, expired/failed auth, service/offline failure, stale state, policy change, and preference/consent persistence failure distinctly. Open only allowlisted authorization URL via existing supported external-link mechanism; never automate browser/native auth. Poll bounded state per contract while pending; provide cancel that invokes `cancelSignIn`; late callback cannot be presented as success unless backend state confirms it. Do not treat callback alone as consent or connection. Permit explicit retry or sign-out on failure; never automatically replay public/setup enablement or consent after stale state. Re-consent requires current-version links and explicit acceptance, without enabling transfer while unresolved.

## Settings: dedicated Online section

Add a minimal `Settings -> Online` section, separate from and not nested under UDP `Connection`. Preserve existing settings navigation and avoid changing unrelated settings. Show connection/account identity only as supplied by DTO, sign-in/re-consent, sign-out, and exact external **Manage Account** link `https://raceiq.snazzie.space/account`; no profile, identity editing, or account-deletion UI.

Show public/private and setup attachment as independent controls with explanatory copy. Use contract `preferences` for effective safety, `persistedPreferences` for last service-confirmed values, and `preferencePersistence` to distinguish unconfirmed/pending/failed writes from confirmation; local draft is separate. Public/setup enablement must not appear effective until persistence succeeds. Turning public off asks backend to install its durable local dispatch barrier; on write failure show effective blocked state and a resolve path, not a claim of service acknowledgement. Setup-off likewise suppresses subsequent attachments even if the write fails. Show consent-required/policy-changed, service unavailable/offline, signed-out, account unavailable, active/blocked sync and bounded queue/error status, and publication withdrawal pending/failed/unavailable without claiming already-sent requests can be recalled. Retry follows stable `retryable`/`retryAfter`; stale revision refreshes state and requires fresh confirmation for permissive changes rather than replaying them.

On sign-out, immediately disable Online actions, hide account-scoped content, cancel queries/pending auth presentation, and show sign-out pending; display confirmed signed-out only when backend state acknowledges it. A transport failure must not falsely claim tokens or remote sessions were cleared. After acknowledgement, isolate/invalidate account-scoped data and never display old account data after switch/sign-out. If backend reports withdrawal limitation or failure, explain truthfully. Keep Online request failures local to this section; unrelated settings and offline use stay usable. Poll only while needed and per contract cadence; suspend when hidden/unmounted.

## Track Detail: Community Laps

Integrate Online board within Track Detail → Laps → Community Laps, alongside existing community content. Reuse `TrackDetail.tsx`, `detail/`, and `CommunityLeaderboard.tsx` composition; keep Online standings separate from local lap rows and existing community boards. Request board by explicit gameId, trackId, carId; never infer a default game from mutable global state or merge results across cars/tracks/games.

Render independent loading, signed-out, consent-required/private, offline/service unavailable, unsupported/unknown identifier, ready, empty, stale cached rows, and unavailable-without-cache/error states. Signed-out/private states must not imply local laps are unavailable. In-app RaceIQ Online standings require a connected account, accepted consent, and confirmed effective public lap sharing. Turning sharing off immediately hides cached rows and blocks requests, including pending or failed preference writes; late results cannot restore access. Explain the mutual benefit of sharing fastest laps and that website leaderboards remain available. Existing community/local queries remain intact. Show stale timestamp/status only while leaderboard access is still allowed; never label unavailable empty rows as a successful empty board. Render only contract public identity fields and lap times/ranks; no email, Discord ID, or local private lap data. Errors translate stable codes; retry respects retryability.

## Data, localization, accessibility

Implement hooks and keys to contract: account state/results scoped by `accountEpoch`; leaderboard key includes `gameId`, `trackId`, `carId`. Cancel/invalidate on sign-out/switch, reject old epoch responses, and apply monotonic revisions. Do not optimistically display server-confirmed consent/preferences/upload capability. Transport failures retain last confirmed state and mark transport failure rather than manufacturing DTOs. Preserve existing local query behavior.

When the backend cannot be reached, show the validated last-known Online account and sharing values instead of replacing them with an error-only page. Persist the sanitized display snapshot across reload; never treat it as authentication or leaderboard authorization. Disable name, sharing, and consent edits until fresh state confirms availability. Keep the account link or sign-in control visible, retain a retry action, and distinguish last-known display from confirmed live status. Unknown account state must not fabricate an account; sign-out removes stored account display before requesting confirmation.

Backend local account persistence is the source of signed-in identity, not cloud reachability or browser cache. Show the account card and known sharing switches during cloud outages and re-consent states; disable remote edits without hiding their last values. A reachable local backend can initiate Discord sign-in even while the Online service or policy endpoint is unavailable. Legacy local records with known choices but no stored public profile show those choices read-only alongside the sign-in control; never fabricate an account name.

Add all visible copy via Paraglide message sources and update every supported locale, including onboarding disclosures, policy/actions, preferences, statuses, errors, accessibility labels, board states, and retry guidance. Keep terminology consistent across onboarding and settings. Follow incumbent accessible semantics: labeled controls, keyboard operation, visible focus, announced pending/error/status changes, non-color-only state, readable responsive layouts, and existing modal/navigation patterns. Do not alter product visuals beyond integration needs; no visual verification is claimed by this plan.

## Deliverables and acceptance

1. **Onboarding presentation/flow:** Welcome leads to selectable Discord/offline cards with one selection-dependent footer action. Get Started and Back belong in the footer. The initial screens, card selection, and offline path have zero Online side effects. Keyboard radio navigation and responsive layouts remain usable. Backend-confirmed authentication precedes permissions and resumes the named permissions step after remount. Public and setup sharing default off and require explicit choices. Consent and preference success are confirmed before setup advances. Back, pending/cancel/failure/re-consent cases remain actionable and truthful.
2. **Online settings:** dedicated Online navigation/section, not UDP Connection; only approved minimal controls; effective vs pending prefs distinguished; fail-closed disable behavior and account isolation honored; exact external account URL; withdrawal limitations disclosed.
3. **Community Laps:** board placed under Track Detail → Laps → Community Laps, separately keyed per game/track/car and not merged with local laps; all loading/identity/consent/private/network/empty/stale/error states distinguishable; readable board remains visible when allowed.
4. **Data integration:** exact shared DTO/action/error contracts and account-epoch/query semantics reused. Fixture-only presentation supports deterministic states before backend availability. Production Hono RPC adapter uses actual exported route AppType only; no runtime mocks, `any`, raw fetch, guessed fallback, credentials, or upload logic.
5. **Locales/accessibility/regression:** every supported locale has complete messages; accessible keyboard/screen-reader and responsive behavior follows incumbent conventions; existing CommunityStep, local laps, community leaderboard, settings, and offline flows remain functional.
6. **Integration gates:** after backend routes/export exist, typecheck adapter against actual AppType and exercise actual state, consent, preference, connect/cancel/sign-out and leaderboard paths. UI fixtures establish presentation only, never policy enforcement. Run repository root `bun run typecheck`, supported-locale compilation, targeted tests, and changed-surface runtime scenario as required by main integration owner. Confirm offline feature availability with Online backend unavailable. End-to-end privacy/security gates (no pre-consent transfer; no private recording/setup upload or validation; setup-off omission; F1 embedded telemetry stripping with local original preserved; account-race isolation; real auth/policy/publication behavior) require backend/service verification and cannot be certified by UI tests alone. Do not claim completion while API/service gates remain unverified.

## Implementation and verification outcome

- Implemented the independent, optional Online onboarding step, dedicated Online settings navigation, explicit current-policy confirmation, separate setup opt-in, acknowledged connection/preferences/sign-out presentation, and fixed external account link. Actual wizard skip completed its callback with zero Online port calls.
- Added Community Laps to both desktop and mobile Track Detail lap composition, leaving local lap rows and the existing Community Leaderboard separate. Car selection is explicit and scoped to the current game/track; only contract public standings are rendered.
- Production `client/src/lib/raceiq-online.ts` implements the exact shared port through the real Hono `AppType`; `client/src/hooks/raceiq-online.ts` shares account generations across consumers, scopes keys by epoch/game/track/car, rejects late responses, and never optimistically confirms consent or enabling preferences.
- Deterministic presentation fixtures remain in Storybook-only sources: `RaceIqOnline.stories.tsx`, `TrackCommunityLaps.stories.tsx`, and `raceiq-online-fixtures.ts`. They are not production fallbacks.
- All twelve locale catalogs contain 101 Online messages with matching keys/placeholders. Paraglide compilation, mobile locale layouts, keyboard interaction, and active-surface axe checks passed. Desktop/mobile settings and actual lap composition were inspected visually.
- Final root `bun run typecheck` passed across client, Storybook, and all workspaces. Focused client response-boundary tests passed: four tests, fourteen assertions.
- Initial browser production-adapter verification exercised all seven methods against an isolated real backend: state reported unavailable service/policy with `uploadAllowed: false`; connect and consent returned `policy_unavailable`, preferences `not_connected`, cancellation `auth_failed`, and the unmapped board `unknown_track`. Current policy configuration—not service reachability—blocks connection and uploads. Existing UI distinguishes these states without DTO, route, enum, or UI changes.
