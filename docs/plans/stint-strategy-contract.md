Status: implemented and verified, including PR #487 correctness corrections. Source: [issue #460](https://github.com/SpeedHQ/RaceIQ/issues/460). User revision: retain stint-average tire wear and fuel beyond session end, reuse them for subsequent stints with the same track/car, and explain historical evidence in the live UI.

Implementation plans: [backend](stint-strategy-backend-plan.md), [UI](stint-strategy-ui-plan.md). Published DTOs and validators live in [`shared/racing/live/strategy.ts`](../../shared/racing/live/strategy.ts) and [`strategy-schemas.ts`](../../shared/racing/live/strategy-schemas.ts). Integration owner owns this contract and shared types; backend owns persistence/derivation/API; UI owns presentation/localization. No unresolved interface choice blocks implementation against this contract.

## Scope and existing authorities

Retain the original issue's persistent estimate history, session stint table/chart, and side-by-side stint comparison. Extend retention to durable SQLite records surviving session end, navigation, reconnect, and process restart. Session end must not clear reusable averages. Clearing estimate history must not delete stint evidence.

Existing code defining integration points:

- `server/telemetry/live-pipeline.ts`: session start, completed/saved lap callbacks, and live pit publication.
- `shared/racing/live/types.ts`: `LivePitData`; `shared/telemetry/live/contracts.ts`: frame context/session identity.
- `server/games/types.ts`: adapter history permissions; preserve `seedFuelFromHistory`, `seedTireWearFromHistory`, and distance-curve policies.
- `shared/games/telemetry.ts`: fuel fraction versus litres; [semantic rules](../reference/semantics.md) govern availability, units, and provenance.
- `packages/analysis-core/src/racing/laps/pit-cycle.ts` and existing pit-cycle tests: reuse game-aware pit classification/evidence, not a second independent game detector.
- `server/db/schema.ts`, `server/db/migrations.ts`: native string car/track identities, session ownership, embedded append-only SQL migrations.
- `apps/backend/src/routes/session-routes.ts`: actual HTTP route location (older architecture prose names `server/routes`).

Do not implement the broad event-timeline/participant architecture proposed in other issues, new simulator acquisition, a service-duration estimator, AI-generated strategy, or a UI redesign. Do not infer wear rates from temperature or fuel litres from an unknown tank capacity. Existing historical sessions are not fabricated into complete stints; this change records newly processed sessions, and explicit session reprocessing can populate old sessions only when source evidence supports it.

## Identity, units, and comparability

Every row carries `gameId: GameId`, `sessionId: number`, `driverKey: string`, native `trackId: string` including layout, and native `carId: string`. Use existing persisted/native driver identity when available; otherwise the explicit install-local `local-player` bucket, labeled as local player, never a guessed name-based identity. Unknown remote driver identity must not join local-player history. Restrict reusable history to `sessions.ownership = "mine"` and the same driver key; imported/other-driver data is not silently included.

Additional compatibility: matching fuel unit and semantic version; matching PI when the game uses PI; matching known tire compound per wheel for tire reuse. Unknown compound matches unknown only and is disclosed. Record available setup/conditions context for explanation but make no unsupported claim that same car/track guarantees identical weather, setup, or driving. Do not pool incompatible units, compounds, or known configurations. Unresolved game/track/car identity disables history reuse; no default simulator.

`CompatibilityContext = { fuelSemanticVersion: string|null, tireSemanticVersions: [string|null,string|null,string|null], setupKey: string|null, conditions: { weather: string|null, airTemperatureC: number|null, trackTemperatureC: number|null } }` is required on every `StintSummary` and `PitEstimateRecord`. Semantic versions identify the consumer derivation and native-channel meaning, not just the aggregation algorithm. An unknown semantic version disables reuse and numerical comparison for that metric. PI must be known and equal when the game uses PI. Tire compounds are checked independently per wheel; a mismatch does not disqualify fuel or unaffected wheels.

`setupKey` is an adapter-provided stable, game/car-scoped configuration identity, not a guessed name or telemetry-derived fingerprint. Equal known keys match; unknown matches unknown only, with an explicit limitation; known versus unknown or unequal known keys disqualify all rate reuse and numerical differences. If an adapter cannot establish a stable setup identity, it supplies null. Conditions are explanatory only, never a compatibility filter or a claim of equivalent driving conditions. A change in PI, setup key, units, or metric semantic versions closes the current stint and rebaselines; no aggregate pools those contexts. UI comparison applies these same rules to the exposed fields, displays both contexts, and shows reasons instead of incompatible numerical differences.

Store fuel in the adapter's packet unit, `L` or `tankFraction`; display tank-fraction consumption as percentage points/lap, not litres or relative percent. Store tire wear as explicit consumer-derived fraction worn, increasing from 0 to 1, only when supported by the semantic contract; UI displays percentage points/lap. Preserve native channel provenance. Pit-snapshot-only wear is not continuous per-lap wear and remains unavailable for that rate unless source evidence spans a known whole-lap interval; do not divide an unlocated pit reading into invented lap rates.

## Durable records and aggregation

Durable strategy tables are introduced by migration v82:
1. `strategy_stints`: stable ID, identity/compatibility fields, ordinal, first/last lap references, start/end source coordinates and wall times, `status: active|completed|interrupted`, boundary reason/evidence, algorithm version, revision, and persisted aggregate numerators/counts.
2. `strategy_lap_metrics`: unique `(sessionId, driverKey, lapId, algorithmVersion)`, stint link, lap time, independent fuel/wheel deltas and quality/exclusion reasons. Store sufficient small source evidence to explain deltas and rederive summaries; do not duplicate raw telemetry.
3. `pit_estimates`: stable ID, identity, stint link, source coordinate, observed wall time, immutable estimate payload and compact source snapshot, algorithm version. A unique source-event key makes repeated processing idempotent.

Use existing lap persistence as the authoritative completed-lap identity. Associate transient completed-lap calculation with the eventual saved `lapId`; persist contribution and updated summary atomically. Publication follows commit. Keep per-frame estimation fast: no frame-rate DB writes, whole-history scans, or raw-history decode.

### Durable source ordering

`SourceOrder = { epochOrdinal: number, sequence: number }` contains nonnegative safe integers, ordered lexicographically. Persist the mapping from stable native/capture epoch identity to an increasing `epochOrdinal` scoped to the session; driver buckets share this order. Within an epoch, `sequence` is the source ingestion sequence, assigned before async derivation, not a timestamp or DB completion order. Allocate an ordinal only for a genuinely new live epoch, durably before publishing its observations. Reconnect/retry/replay retains the original mapping and sequence; replay/reprocessing never allocates a fresh live epoch or appends estimate observations. Reprocessing replaces derived summaries only and leaves surviving immutable estimates unchanged.

Every `PitEstimateRecord` requires `sourceOrder: SourceOrder`; retain `sourceCoordinate` for native time interpretation, never ledger ordering. Order history by `(epochOrdinal, sequence, id)` descending across all requested driver buckets. Cursor payloads bind the session, game, driver filter, clear generation, and ordering tuple. Newer inserts cannot move already paged records.

Serialize clear with source admission and pending estimate writes for that session/driver: persist a watermark through the highest admitted `SourceOrder`, delete its existing ledger, and increment a durable clear generation atomically. Pending observations at or below that boundary cannot commit later; reject their writes against the watermark. Subsequent live observations above it may append, including a new epoch whose native milliseconds restart at zero. Clear is a boundary even when no estimate rows exist. A cursor spanning all drivers binds every affected clear generation and becomes invalid when any included driver is cleared. Persist epoch mappings, admission high-water marks, and clear generations across restart; neither wall-clock changes nor opaque epoch-string sorting affects them.

Use existing durable capture/source sequence metadata where available; source admission here means admitting an estimate-producing observation into the ordered strategy write queue, not writing a database row for every telemetry frame. Serialize clear through that same queue before acknowledging success. The watermark covers all already admitted observations even if their estimate writes are still pending.

The live pipeline assigns a private monotonic ingress coordinate before detector feed. Admission keys use that coordinate with the captured session/epoch, not native milliseconds: distinct inputs at the same native time remain distinct, while retries and shutdown retain the original input identity. Admission allocation is FIFO; a transient failure retains the original observation and blocks later admissions from overtaking it. Clear pauses ingress and admits the last received point before advancing its watermark.

Contributions are staged in a compact accumulator and promoted to live state only after the contribution/summary transaction commits. Failed contributions retain the last committed rates/counts and retry without double counting. A terminal core lap-save failure has no authoritative saved identity, so its pending strategy job is settled and skipped rather than blocking later laps or session rotation. Deleting a source cancels only that source's pending writes/admissions, including in-flight completion guards.

Stints start at the first trustworthy baseline for a session/driver. Close/start at a proven pit visit/service boundary, driver/car/track change, or timebase discontinuity. Reuse existing pit evidence; drive-throughs may split an operational stint but must not imply fresh tires. Unproven boundary is labeled inferred/unknown. Service mid-lap invalidates that metric's interval; no lap delta spanning a refill or tire replacement. A new tire set resets tire curves/histories; a drive-through does not reset tire age. New stint clears current-stint rate samples, then obtains compatible history.

Per completed uninterrupted lap: fuel use = start fuel − end fuel; wear = end fraction-worn − start fraction-worn per wheel. Zero is valid when both measurements are valid; negative differences indicate service/reset or invalid evidence, never clamp into valid zero. Reject nonfinite/out-of-domain values and gaps lacking reliable endpoints. Fuel and each wheel have independent eligibility/counts; fuel absence must not discard valid tire evidence. Exclude partial, pit-entry/exit/service, invalid, or discontinuous laps from reusable rate averages, recording reasons. Summary completed-lap count includes all fully recorded laps; rate counts identify the narrower eligible population. `measuredFuelUsed` sums trustworthy positive/zero consumption intervals, excludes refill amounts, and is labeled partial if coverage is incomplete; it is not claimed to equal total tank consumption. Average lap time uses valid full non-pit laps with its own count.

Historical baseline: select the latest 20 completed/interrupted compatible prior stints with at least one eligible metric sample, ordered by end time then ID; exclude the current stint and active unfinished stints. Compute each metric as sum of eligible deltas / its eligible lap count, not an unweighted mean of stint averages. Report the exact contributing sessions/stints/counts; take compound/PI/units into account before applying the bound. Current-stint fuel takes over after 2 eligible laps, each tire after 3; before then use history if adapter-permitted, otherwise available current samples marked provisional. Never insert historical pseudo-laps into current averages. Preserve existing current-stint rolling limits (fuel 5, tires 3) and supported distance-based projection after tire evidence exists. No historical distance curve is invented from scalar averages.

## Shared DTO boundary

All keys shown below are required unless explicitly optional; `null` means unavailable, never measured zero. Timestamps are UTC ISO strings; source coordinates retain their time domain/epoch and must not masquerade as wall time. Numeric values must be finite.

- `MetricRate = { value: number|null, unit: "L/lap"|"tankFraction/lap"|"wearFraction/lap", eligibleLaps: number, source: "history"|"current-stint"|null, provisional: boolean, unavailableReason: string|null }`.
- `StintSummary = { id: string, sessionId: number, driverKey: string, ordinal: number, status, gameId, trackId, carId, pi: number|null, compounds: [string|null,string|null,string|null,string|null], startedAt: string, endedAt: string|null, boundary: { reason: string, confidence: "observed"|"inferred"|"unknown" }, completedLaps: number, fuel: MetricRate, tires: [MetricRate,MetricRate,MetricRate,MetricRate], measuredFuelUsed: number|null, fuelUnit: "L"|"tankFraction", fuelCoverage: "complete"|"partial"|"unavailable", averageLapSeconds: number|null, paceLaps: number, exclusions: { reason: string, count: number }[], algorithmVersion: string, revision: number }`.
- `HistoricalBaseline = { fuel: MetricRate, tires: [MetricRate,MetricRate,MetricRate,MetricRate], evidence: { metric: "fuel"|"fl"|"fr"|"rl"|"rr", sessionId: number, stintId: string, eligibleLaps: number, endedAt: string }[], lastObservedAt: string|null, limitations: string[] }`. Distinct counts derive from these references, not invented confidence percentages.
- `PitEstimateRecord = { id: string, sessionId: number, driverKey: string, stintId: string, observedAt: string, sourceCoordinate: { epoch: string, domain: "session"|"wall-clock", milliseconds: number }, trigger: "lap-completed"|"limiter-changed"|"stint-ended", pitInLaps: number|null, estimatedPitTime: { sessionElapsedSeconds: number|null }, limitedBy: "fuel"|"tires"|null, tyreChangeSuggestion: "consider-change"|"not-indicated"|"unavailable", fuelChangeSuggestion: "consider-refuel"|"not-indicated"|"unavailable", fuel: MetricRate, tires: [MetricRate,MetricRate,MetricRate,MetricRate], sourceSnapshot: { fuelRemaining: number|null, fuelUnit: "L"|"tankFraction", wear: [number|null,number|null,number|null,number|null], lapId: number|null }, algorithmVersion: string }`.

`StintSummary` also requires `firstLapNumber: number|null` and `lastLapNumber: number|null` for the recorded lap range. `PitEstimateRecord` also requires `baseline: HistoricalBaseline|null`, frozen at observation time, so historical records retain their original evidence references and counts. The shorthand `status`, `gameId`, `trackId`, and `carId` uses the enumerated status and identity types defined above. Summary metrics always describe that stint's measured population (`source: "current-stint"` when available); they never contain historical fallback rates.

`HistoricalBaseline` also requires `historyRevision: number`, a nonnegative safe integer for its `(gameId, driverKey)` history namespace. The required `compatibility: CompatibilityContext` field on summaries and estimate records contains the context defined above; immutable records freeze it alongside their baseline. A frozen historical revision identifies the snapshot used, not a demand that old records follow later history changes.

To make the common row-identity rule explicit, `PitEstimateRecord` also requires frozen `gameId: GameId`, `trackId: string`, `carId: string`, `pi: number|null`, and `compounds: [string|null,string|null,string|null,string|null]`. These values are captured with the observation, not joined from a session that may later be corrected. Pending writes must validate the current session identity before committing; corrections cannot resurrect evidence under the previous context.

`estimatedPitTime` means projected session elapsed time to pit, never pit-stop service duration: current session elapsed + `pitInLaps × representative lap seconds` only when all inputs are trustworthy; otherwise null. Suggestions reflect the existing limiter/thresholds, not unimplemented optimal strategy, refill quantity, or service-duration advice. Snapshot at eligible completed laps, limiter transitions, and stint closure, deduplicated at identical source coordinates; never log every 30 Hz frame.

Extend live pit context with `strategy: { sessionId, driverKey, stintId, revision, historyRevision, fuel: MetricRate, tires: [...], baseline: HistoricalBaseline|null, persistence: "ok"|"error" }`; preserve existing live numeric estimates for their existing consumers while updating provenance consumers to per-metric source. Reconcile old `estimateSource` consumers with this authoritative provenance; remove misleading single-source UI wording. WebSocket notifications `strategy-updated` carry session/driver/stint/revision only, after commit; clients refetch summaries/history rather than receiving the full ledger every frame. Cross-session baseline changes use the separate history notification below.

Example: a compatible prior stint has 10 eligible laps, 24 L consumed, and FL wear delta 0.08. Baseline fuel = 2.4 L/lap; FL wear = 0.008/lap (0.8 percentage points/lap). At 24 L remaining the existing fuel projection gives 10 laps. After two eligible current-stint laps consuming 2.6 L each, fuel source becomes current-stint (2.6 L/lap); FL can still be historical until three eligible tire laps exist. Display never calls the current rate a previous-session measurement.

Malformed params/header/cursor/body: 400 `{code:"INVALID_STRATEGY_REQUEST",error:string}`. Unknown/cross-game/inaccessible session or stint: 404 `{code:"STRATEGY_NOT_FOUND",error:string}`. Clients reset filtered and all-driver cursors for that session and refetch. This notification is separate from reusable-evidence changes: clear does not increment `historyRevision`, change stint summaries, or rewrite surviving estimate snapshots.

### Cross-session history synchronization

Persist one monotonically increasing `historyRevision` per `(gameId, driverKey)` independently of session rows, so deletion cannot reset it. In the same transaction as any change to reusable evidence or eligibility (stint finalization, deletion, ownership/identity correction, or rebuild activation), increment every affected old/new namespace revision. Estimate-history clear does not change reusable evidence and therefore does not increment this revision. Emit post-commit `strategy-history-updated: { gameId: GameId, driverKey: string, historyRevision: number }`, without requiring a source session/stint to survive deletion. This deliberately invalidates the whole game/driver namespace rather than maintaining fragile cross-session dependency lists.

Baseline reads return rates/evidence and `historyRevision` from one consistent DB snapshot. Before publishing another live strategy value or serving a cached baseline, compare its revision with the committed namespace revision; an outdated baseline is unusable. Mark affected active trackers dirty and reload compatible summaries, preserving current-stint samples and independent takeover thresholds. While refresh is pending, use eligible current samples provisionally or null with `history-refresh-pending`, never the invalidated historical rates; genuine storage failure retains the existing persistence-error behavior. Guard reload results by both live identity/generation and history revision so a delayed read cannot restore deleted evidence.

On `strategy-history-updated`, clients invalidate all baseline queries in that game/driver namespace, including other sessions, and discard responses/live history-derived values below the highest observed revision until refreshed. Baseline query keys also include target `stintId`; history-page keys include cursor and driver filter. Mount/reconnect always refetches to recover missed notifications. Existing immutable estimate records remain unchanged; only advisory baselines and current strategy refresh.

## Lifecycle and failure handling

- Session end finalizes summary but retains all records. Crash preserves committed contributions; on next startup mark unclosed stints interrupted, not service-completed. Reconnect resumes only a confirmed same source epoch/session; otherwise interrupt and rebaseline.
- Replay of identical source/lap keys is idempotent. Explicit reprocessing stages a versioned replacement of derived stint contributions/summaries, validates, then activates transactionally; no partial visible rebuild and no doubled baseline counts. Reprocessing never appends estimate history or changes surviving immutable estimates. Clear watermarks, source admission serialization, and retained epoch mappings follow the durable source-order rules above; only genuinely new live observations above the clear boundary may append.
- Session deletion cascades records and clear markers; identity corrections invalidate/rebuild matching summaries and baselines before serving them under a new identity. Raw-capture cleanup alone does not delete already persisted summaries; deleting the session does.
- Pending old-session history reads/writes cannot enter a new live stint: guard results by session/driver/epoch/generation. Store ordering is deterministic across concurrent clients and processing retries.
- Storage errors do not freeze telemetry or claim persisted success. Surface degraded persistence, retain last committed data, and expose errors for failed API operations. Do not retry by adding duplicate contributions; recovery uses stable keys and existing lifecycle/error conventions.
