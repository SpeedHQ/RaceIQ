# Discord dashboard authentication contract

## Approved behavior and ownership

Discord-enabled installations use Discord sign-in for dashboard access. Offline installations retain password or explicitly acknowledged unprotected access. Onboarding presents these choices on one screen; it never asks Discord users to configure a dashboard password. Discord account identity must be verified server-side, not inferred from a browser flag or an installation-wide connected indicator.

The coordinator owns this contract and integration verification. [UI plan](discord-dashboard-auth-ui-plan.md) and [backend plan](discord-dashboard-auth-backend-plan.md) implement it independently. Existing ownership semantics are authoritative in [CONTEXT.md](../../CONTEXT.md), and `server/db/local-account-queries.ts` defines the single-account ownership constraint. Existing host/origin, CSRF, HttpOnly session, recovery-marker and environment-override protections remain in force.

## Public boundary

Extend `GET /api/auth/status` with required `method: "discord" | "password" | "none" | null`. Null means unconfigured. Existing fields retain their meanings; `protected` is true for Discord and password. `authenticated` requires a session belonging to this browser when protected. `SERVER_PASSWORD` remains an explicit administrator override and reports password mode.

Add these Hono RPC operations:

- `POST /api/auth/discord/start`, JSON `{ language?: string }`, validated against supported locales. Success: HTTP 200, `{ authorizationUrl: string, expiresAt: number }`, where expiry is Unix milliseconds. Set a short-lived, random HttpOnly, SameSite=Strict browser-flow cookie, Secure on HTTPS. The authorization URL is from the existing Discord OAuth provider, never caller-supplied. Starting again replaces this browser's attempt. Reject invalid origins, conflicting configuration or unavailable provider with a generic error.
- `GET /api/auth/discord/callback`: the worker's browser PKCE flow validates callback state/nonce, PKCE, expiry and single use. Verify the returned account with the real Online service and enforce the installation owner. Do not issue a dashboard session merely because a callback succeeded. Store a short-lived completion bound to the initiating flow and redirect to its stored, validated dashboard origin at `/login?discord=complete`. Never put credentials or session grants in redirect URLs. The callback may be reached cross-site, but only this narrowly scoped route gets that exception.
- `POST /api/auth/discord/finish`, JSON `{}`: require the initiating browser's HttpOnly flow cookie. HTTP 200 `{ status: "complete" }` sets the normal dashboard session cookie and `X-RaceIQ-CSRF`; HTTP 202 `{ status: "pending" }` means the callback has not completed. Missing, expired, consumed, canceled or mismatched flow returns an error without access. Completing initial setup atomically selects Discord protection and preserves settings/recordings. Initial Discord sign-in also connects Online using that verified identity; do not require a second Discord dialog. A subsequent dashboard login must not disconnect or switch the installation's Online account.
- `POST /api/auth/discord/cancel`, JSON `{}`: cancel only this browser's flow and clear its transient cookie; HTTP 200 `{ ok: true }`. Do not downgrade configured protection.

Errors use `{ error: string }`: HTTP 400 invalid input or invalid OAuth completion; 401 missing/invalid browser proof; 403 wrong installation account; 409 conflicting/stale configuration or environment override; 429 bounded-attempt limit; 503 provider/worker unavailable. Never expose provider tokens or internal exception details. Do not expose general Online state, settings, recordings, Studio or WebSockets before dashboard authentication.

Example: pending status `{ method: null, pending: true, protected: false, authenticated: false, ... }`; completed Discord status `{ method: "discord", pending: false, protected: true, authenticated: true, csrf: "<browser-session-csrf>", ... }`. A different browser receives the same method but `authenticated: false` and `csrf: null`.

## State transitions and security

- Pending → verified Discord completion → Discord-protected dashboard plus connected Online account; no password step, no unprotected intermediate state.
- Pending → offline selection → existing password/unprotected setup, with existing validation and explicit exposure warning.
- Existing verified Online account → Discord dashboard mode on startup or successful connection. Bind to the existing installation owner, invalidate incompatible password sessions and require independent browser proof; a globally connected account never authenticates another browser.
- Existing password/unprotected mode → authenticated user connects Discord → switch to Discord protection only after verified identity. Preserve explicit `SERVER_PASSWORD` override. An existing browser without this flow's proof may need to sign in again.
- Discord sign-out, provider failure or worker failure never changes mode to unprotected. Local dashboard logout revokes that browser's session. Recovery through the existing explicit local auth-reset command remains possible.
- Wrong account cannot take over an existing installation. Concurrent setup, cancellation, restart and stale callback completion cannot change protection or issue access after their configuration/flow generation has changed. Outstanding attempts are bounded and expire; restart invalidates unfinished attempts.
- Changing an existing password-protected installation to Discord requires its current authenticated dashboard session and CSRF at start, with authorization revalidated before commit. Public Discord bootstrap cannot replace existing password protection or persist installation settings. Persist a setup language choice only during pending setup or successful authorized completion.
- Completing another login in already configured Discord mode does not change the protection revision or invalidate other browsers. Recheck flow liveness after write admission and immediately before commit; canceled or expired attempts cannot mutate ownership or protection while queued. Serialize duplicate finish requests per attempt.
- Authentication is independent of consent and public-sharing choices. Do not silently enable sharing or require publication consent to sign in.
- Preserve network-address behavior. Use the initiating dashboard's validated external origin for the callback where the provider permits it; do not assume every browser's localhost is the server. Provider redirect-allowlist limitations must be reported, not worked around by disabling protection.

## Development isolation and production rejection (additional approved requirements)

Source development must not contact the production RaceIQ API. `resolveOnlinePlatform` returns a production platform only for `NODE_ENV=production` outside E2E. Ordinary development defaults to disabled Online transport. Explicit development requires all of `RACEIQ_DEV_ONLINE_ORIGIN`, `RACEIQ_DEV_AUTH_ORIGIN` and `RACEIQ_DEV_AUTH_PUBLISHABLE_KEY`; the Cloud API origin may be literal loopback HTTP(S) or the dedicated approved development tunnel origin `https://raceiq-dev.snazzie.space`. No other remote application API origin is allowed. The user approved reusing the existing hosted Supabase authentication and Discord provider: an explicitly configured HTTPS authentication origin may be hosted, with no path, query, fragment or credentials. This does not authorize production RaceIQ API requests or implicit authentication defaults. Partial or malformed configuration fails closed. Development credentials remain ephemeral and separate from the production OS keystore. Existing E2E strict loopback/HTTPS rules remain unchanged. Disabled mode must not construct the SDK, read production credentials, preconnect, or start an OAuth flow. Authentication-unavailable errors must explain configuration requirements without changing protection.

Every desktop-to-Cloud API request carries `X-RaceIQ-Client-Environment: development` for source dev/test or `production` for production runtime. The exact-origin development transport rejects production URLs and redirects regardless of headers. The Cloud API server in `/Users/acoop/orca/projects/raceiq cloud` adds a configurable `ALLOW_DEVELOPMENT_CLIENTS` policy, false by default. Local development launchers explicitly enable it. When false, a declared development request receives HTTP 403 with the existing API envelope and code `development_client_forbidden`, before application side effects. Malformed/duplicate environment headers fail closed; absent headers remain compatible with existing website/SDK clients. Health and human-facing static pages need not require a desktop marker.

This marker enforces ordinary client/deployment policy, not tamper-proof binary attestation: a modified client can forge a production declaration. Do not describe it as proof of an official binary.
