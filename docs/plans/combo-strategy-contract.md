# Combo-pinned race strategy contract

Plans: [backend](combo-strategy-backend-plan.md), [UI](combo-strategy-ui-plan.md). Integration owner: coordinator. Boundary decisions below are agreed from the user requirement and existing game/car/track applicability rules, not a new session-owned model.

## Identity and persistence

One selected race plan per exact `(gameId, carId, trackId)` tuple. Source session/stint fields remain evidence only. Selection survives session changes, restart, and switching to another combo. Selecting a plan replaces only that combo's selection; unloading/deleting affects only that combo. Preserve existing FM PI applicability check: pinning is by three-part combo, but a mismatched or unknown PI must not apply the selected plan. Unknown car/track never selects a plan. Game/car/track use existing validated IDs and case-sensitive equality. Editing a selected plan to change identity clears its old selection; do not silently move its pin or overwrite another combo. Plan CRUD/evidence/forecasts otherwise retain behavior.

Migrate the existing singleton active_race_plan selection into a new composite-key table with game_id/car_id/track_id and plan_id referencing race_plans with cascading selection deletion. Copy the existing selected plan's identity and ID atomically, then remove obsolete singleton table/schema/code. Use the repository migration ordering/version conventions; never edit an already-applied migration. Existing saved plans remain unchanged.

## API and shared schemas

Preserve auth/CSRF/origin/error middleware. Replace GET `/api/race-plans/active` response with `{ plans: RacePlan[] }`, one selected plan per tuple, deterministically ordered by game/car/track. No input required. UI reads all pins and picks exact live combo, never the first plan or last globally selected plan. PUT `/api/race-plans/active` takes `{ gameId: GameId, carId: nonempty trimmed string <=200, trackId: nonempty trimmed string <=200, planId: string <=200 | null }`; all fields required, no nullable combo. Existing non-null ID must belong to that exact tuple or return 400 INVALID_RACE_PLAN without writes; missing plan returns 404 RACE_PLAN_NOT_FOUND. Null unpins only that tuple. Response remains `{ plan: RacePlan | null }`. Shared authoritative schemas/types live in `shared/racing/live/race-plan.ts`: `RacePlanComboSchema`, inferred `RacePlanCombo`, `ActiveRacePlansResponseSchema`, and `SetActiveRacePlanInputSchema` (and inferred `SetActiveRacePlanInput`). Existing ActiveRacePlanResponseSchema is retained for PUT only, not as a GET compatibility shim. Example: PUT `{gameId:'acc',carId:'301',trackId:'7',planId:'p1'}` pins p1 only for that combo.

Host boundary: `activePlans(signal?)` returns GET response; `setActivePlan(input: SetActiveRacePlanInput)` returns PUT response. Hook names: `useActiveRacePlans()` and `useSetActiveRacePlan()`; the mutation accepts complete input. Keep a shared active-query prefix for invalidation. No obsolete `useActiveRacePlan` alias/re-export. All callers, client adapter, tests and stories must migrate. Worker backend owns server/schema/migrations/tests; worker UI owns host/hooks/client/UI/stories; coordinator owns shared schemas/contracts and final integration.

## UI and stories

Saved strategy rows show each combo's loaded plan, and activation/unload submits that row's exact tuple. Live PitEstimate/expanded LiveRaceStrategy select by exact current game/car/track and retain PI checks; unmatched/unknown identity uses automatic estimates, never a different combo's selected strategy. Session evidence is not a selection key. Existing list may display all plans for selected game with clear car/track identity; if filtering by context, preserve access to other combos via explicit controls. Planner unload must target its saved plan's combo, not globally unload. Add typed actual ACC dashboard stories for matching selected plan, approaching pit stop, fuel shortfall, and unmatched combo with automatic estimate fallback; seed actual query state, not a fake renderer or production data fallback.

## Acceptance and end-to-end evidence

- C1 persistence/API: Pin A then B with different tuples; GET lists both. Unpin/delete A leaves B. Restart retains B. Wrong tuple+ID fails without changes. Same tuple replacement retains exactly one selection.
- C2 live: Native live input selects A on combo A, B on combo B, automatic estimates on unmatched/unknown identity. Same combo in a new session restores its pin. FM PI mismatch remains inapplicable.
- C3 cutover: Existing singleton upgrade preserves its original combo pin and all saved plans; no obsolete global-selection code/callers remain. Editing identity clears prior pin rather than moving it.
- C4 UI/story: Multiple rows can show Loaded for different tuples; unload one leaves others loaded. Actual dashboard story states render correct selected plan/stop/fuel warning/fallback at desktop and 390px, keyboard focus visible and no document overflow.

Coordinator reuses feature integration `race-plan.test.ts` and E2E `race-plan.spec.ts` compiled isolated runtime/native F1 inputs. E-C3: isolated pre-upgrade singleton DB -> actual migration startup -> same original pin and plans, then real API and live UI (C3). Integration/unit/static gates supplement these scenarios; they do not replace real app integration. Workers skip builds/tests/lint/formatters. Coordinator runs full affected test modules, not only new cases. Unexecuted/blocked scenarios are not passing evidence.
