# Selected-strategy adherence and adaptive pit window

Implementation: [UI/data plan](strategy-adherence-ui-plan.md) and [live producer plan](strategy-adherence-backend-plan.md). Existing boundaries: [combo pins](combo-strategy-contract.md), [stint evidence](stint-statistics-contract.md). User chose recalculated live windows after early/late service. This change consumes existing live strategy, stint summaries, pit-estimate history, session-lap metadata and telemetry; no backend endpoint or DB change is required. Saved plans remain immutable comparison baselines.

## Observable behavior

A1: Selected applicable strategy displays a primary adherence graph in the incumbent pit panel. Separate fuel-remaining and four-wheel tire-wear scales; dashed reference from planned rates, solid observed checkpoints/current point. Clearly identify current lap, original next planned stop, and shaded adaptive pit window. Labels, not color alone, communicate within/over/unknown. Existing automatic panel remains for unmatched identity.

A2: Current resource state and remaining race distance determine the live pit window, not merely original stop laps. Early/late refuel/tire service updates actual state and recomputes the window without changing saved stops. Fuel-only service retains actual worn tires. Passing pit entry alone does not add fuel or fresh tires. Never infer a completed stop count from summary ordinal, pit entry, or incomplete history. Display estimated future stops, not an invented total historical count.

A3: No fabricated observed history, extrapolated past samples, incompatible units/compounds, stale historical rates labeled as live, or green missing-data state. Current-session/current-driver/current-stint history only, matched to actual lap IDs. Break actual traces at missing laps or observed resets; do not connect through service. Recent page of history is explicitly recent evidence; no claim of full-session history. Current point requires valid lap fraction; missing position remains unknown rather than fabricated interpolation. Rewind/session/combo/stint changes cannot retain another source's trace.

A4: Per-metric adherence compares measured current-stint rate (at least two eligible laps) against compatible planned source rate, plus current resource limits. Display-resolution rounding may suppress floating-point-only differences, but window limits use unrounded values. A reference resource-level line is anchored to an observed checkpoint in the current resource segment, not an assumed starting fuel load or fresh current tires. Reset fuel and each tire independently when actual resources reset. No anchor/history means an observed dot and unknown trajectory, not a manufactured past line. Reference may project forward using explicit planned rates.

## F1 2025 no-refueling rule

The authoritative feature rule is `supportsRaceRefueling` in `contracts/race-rules.ts`: F1 2025 race stops cannot replenish fuel; other supported games retain their existing behavior. Measured fuel levels, usage statistics, and consumption comparisons remain valid. Fuel must never be presented as a reason to pit or a resource restored by an F1 stop.

- F1.1: Automatic and adaptive F1 pit windows use tire constraints only. Low, missing, incompatible, or faster-consumed fuel cannot create, advance, postpone, or suppress a tire window. Fuel remaining-lap pit estimates and refueling suggestions are absent.
- F1.2: Generated/recalculated F1 stops are tire-limited, never fuel-limited. The existing initial race fuel budget may still be validated; an insufficient whole-race budget produces no safe proposal, not extra fuel stops. Generated per-stint starting fuel decreases from the single initial load. No stop restores it, including across recalculated compound phases.
- F1.3: F1 UI hides fuel adherence plots and inter-stop refueling actions/projections. Measured fuel remains available in the existing fuel telemetry and stint statistics. Future-window assumptions mention fresh tires only; finish text claims tire life, not enough fuel/resources. No future F1 fuel extrapolation or implied replenishment is permitted.
- F1.4: Native F1 E2E changes fuel without changing tires and observes unchanged tire bounds, then changes wear/replaces tires before/after the original target and observes appropriate adaptation with saved plan unchanged. Initial fuel is set before the run; no F1 refueling fixture is legal. Refueling-capable games retain fuel-limited windows and fuel-only/combined service behavior, covered by existing real native tests and focused feature integration/model cases.

E-F1 maps F1.1–F1.4 to the full compiled `race-plan.spec.ts` module and corrected F1 generation/recalculation scenarios. E-A2 refueling checks apply only to games supporting race refueling; F1 covers tire service without adding fuel. Missing fuel can make the fuel/adherence evidence unknown without invalidating an otherwise known F1 tire-only window.

The production telemetry boundary is the existing live semantic schema/frame: `timing.lap-fraction` is an optional numeric fraction, with resolution/freshness metadata. ## Adaptive window calculation

Fuel capacity, reserve, range and future replenishment below apply only to games supporting race refueling. F1 omits those constraints and prerequisites entirely; its current and future ranges use tires only.

Completed race distance x = currentLap - 1 + lapFraction. Finish T = plan.totalLaps. Current fuel range = (actual fuel - reserve)/fuelRate. Each tire range = (cliff wear fraction - actual wear)/wearRate. LMU energy range = (actual energy - energy reserve)/energyRate. Zero consumption yields unbounded range only when resource is not already beyond its reserve/cliff; exhausted resource yields zero/overdue. Minimum gives current range C and limiter. Use configured `plan.generation.fuelCapacity/fuelReserve`; absent settings make complete window unknown, never assume a zero reserve. Check a reported physical capacity when available; a planned capacity exceeding it cannot produce a green feasible window.

At or beyond reserve/cliff means exhausted (zero range), including zero-rate metrics; do not claim unlimited life for an already exhausted resource. A physical fuel capacity greater than the configured planned load is valid; reject the opposite mismatch. Missing/unknown semantic versions cannot establish a compatible planned reference. An overdue latest lap returns the explicit overdue state rather than a generic unknown/infeasible range.

Future full-stint range F uses planned capacity minus reserve, fresh tires with the SAME observed compound set, and full LMU virtual energy minus reserve, divided by corresponding compatible current rates or provisional planned rates. Do not borrow a rate from a different compound or silently assume future mixed-compound phases. When no same-compound future basis can be established, report unknown window instead of inventing future capacity. The forecast explicitly assumes that refuel load and those fresh compounds at future service; actual current tires/fuel are never reset by the forecast.

If C >= T-x: finish without further resource stop. Otherwise estimated future service count k = ceil((T-x-C)/F), requiring positive usable F and bounded <=100; unbounded F needs exactly one stop. Earliest feasible next stop = max(currentLap, ceil(T-k*F)); latest = min(T-1, floor(x+C)). Handle floating arithmetic epsilon only, not a hidden resource margin. A current resource already exhausted or latest < currentLap means overdue/pit now. Earliest > latest or unusable future capacity means infeasible/unknown with explicit reason, not a reversed range. Open/upcoming derives from current lap versus earliest/latest. Original next planned stop is a separate immutable marker, never substituted for the adaptive range. After any observed resource change, recompute from x and actual resources; no stored-plan mutation or synthetic stop-count advancement.

## LMU native-live correction

The integration boundary remains the existing LMU native source, live schema/frame, strategy and history APIs. Test composition replaces only the OS shared-memory reader; production `LMUTelemetrySource`, context encoding, parser, live pipeline, persistence, HTTP/WebSocket and browser UI remain real. No production test endpoint or fixture fallback is permitted.

The authoritative native field is optional `LMUExtendedData.lapDistancePct` in `shared/telemetry/lmu.ts`, projected through the existing `timing.lap-fraction` catalog mapping with unit `fraction`. It is native player lap distance divided by positive native scoring track length, including valid endpoints 0 and 1. Missing scoring, nonfinite/negative/out-of-range distance, or invalid track length omits the field and yields unavailable position; no zero fallback is permitted. The field uses native scoring time through `lmuSourceTimestamp`, never the faster physics clock or receipt time.

- LMU-L1: Controlled native historical and current sessions produce fresh fractional position, litre fuel, four-wheel wear and fraction-valued virtual energy. After the existing producer's three-eligible-lap threshold, the pinned matching plan displays measured adherence; incompatible identity remains automatic/unknown.
- LMU-L2: With fuel and tires sufficient, measured virtual energy independently determines the current window. Lowering energy alone advances the deadline; fuel-only replenishment cannot restore energy or tires. Window calculations retain unrounded authoritative rates.
- LMU-L3: Missing/invalid native virtual energy or stale native scoring produces an explicitly unavailable window and no green state while valid physics-backed fuel/tire traces remain. Restoring the actual native value or scoring timestamp recovers the window; source freshness checks are not bypassed.
- LMU-L4: Actual fuel/energy service and subsequent admitted laps update only observed resources and recompute bounds. Saved plan GET remains unchanged through depletion, missing-value recovery and service. New native session/identity cannot reuse old current-stint evidence.
