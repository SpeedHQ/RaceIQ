# Online uploads, community replay and driver attribution

Status: implementation authorized on 2026-10-23. The user approved minimal canonical identity tables, then deferred all profile work and explicitly requested removal of profile-sync code. This document replaces earlier Online plans. Implementation does not authorize commits, deployment, SDK publication or desktop control. No ADR is required or recreated.

## 1. Scope and ownership

The OSS UI and local app backend are untrusted clients. The **hosted Online service**, not the local app backend, owns authoritative validation, anti-cheat, acceptance and publication.

| Owner | Responsibility |
| --- | --- |
| Game/shared/capture layers, outside `packages/online` | Derive native-driver attribution from recorded packets at lap finalization; publish completed lap/source data |
| Local lap/data feature | Finalize lap and attribution, mark evaluation once, conditionally update FK-backed fastest game/track/car table |
| `packages/online` | Sequential upload cron, auth/consent/privacy, community leaderboard/download/import/replay orchestration |
| App platform | Shared schema/migrations, DB write authority, process lifecycle and existing host composition |
| Hosted Online service | Existing API/idempotency, authoritative validation and anti-cheat |

Community download/import/replay and native-driver attribution remain in this PR. Attribution belongs outside Online. All new profile work, including `packages/profile`, is deferred; remove existing profile synchronization and its exclusive preparation/delivery machinery while preserving local dashboard/driver-summary metrics. AI startup/chat-memory refactoring and upgrade/rollback harness enhancements must leave this PR.

There is **no upload queue**: no outbox table/database, pending/uploading columns, persisted reference queue, desired-state copy, reconciliation feed, receipt cache or queue admission. The upload cron reads the fastest-combo table joined to lap outcome columns and processes one selected lap after another. The cron delivers data; it never populates the winner table or reevaluates lap history.

Online does not repair sources, reconstruct attribution, resume reprocessing, rebuild profile contributions, scan for historical fallback or implement anti-cheat locally. Keep necessary wire-format validation, original identifiers, credential safety and setup sanitization. Existing community import journal recovery remains legitimate import-owned behavior, distinct from upload-source repair.

No new UI redesign, service/API redesign, game support or retrospective statistics correction is included. Preserve existing auth/settings/status/community/replay surfaces. If genuinely new UI implementation is necessary, agree separate UI/backend plans against a shared contract first.

A copied database/recording from a different installation, mismatched origin or unknown historical origin is not assumed local. ### Agreed implementation seams

- App DB owns the schema, native identities, installation origin, atomic finalization and winner initialization. `server/db/online-upload-queries.ts` exposes `getOnlineUploadWinnerPage(afterLapId, limit)`, `readOnlineLapUpload(lapId)`, `retainOnlineLapRequest(lapId, request)`, `settleOnlineLapUpload(lapId, idempotencyKey, result, remoteJobId, uploadedAt)` and `setOnlineLapRetryAfter(lapId, idempotencyKey, retryAfter)`. Reads recheck current winner, Self validity and trusted recording origin. Request retention is compare-and-set and cannot change immutable request bytes/identity or assign another account. Settlement updates only the matching surviving lap/request. Upload pagination is ascending lap ID, bounded and independent of historical initialization.
- A winner page returns `{ items, nextCursor }`; each item identifies `lapId`, native `gameId`/`trackId`/`carId`, and integer `lapTimeMs`. Request state uses `accountId`, `idempotencyKey`, `identityJson`, `payloadFingerprint`, nullable `reservationToken`, nullable terminal `result`, nullable `remoteJobId`/`uploadedAt` and nullable protocol `retryAfter`. There is no durable attempts/active-upload state. Online injects these operations into its worker; the package does not import the app DB.
- App-owned status storage exposes `readLapUploadItems(accountId, view, boundary, limit)` through injected `OnlineLocalPlatform`, returning existing public `UploadItem` records. `view` is `"queue" | "history"`; nullable `boundary` is `{ time: number; id: string }`. Stable IDs are `lap:<lapId>`. Awaiting rows sort by evaluation timestamp/ID ascending; terminal history sorts by outcome timestamp/ID descending, with strict cursor boundaries. The legacy `admittedAt` field represents evaluation time, not queue admission; `attemptCount` is nullable unknown, `nextAttemptAt` is protocol retry time and `acceptedAt` is matching receipt confirmation time.
- Existing status views are projections, not a preserved attempt ledger: awaiting rows are current eligible winners without terminal results; history is retained lap terminal results. Unsupported historical attempt counts are nullable/unknown, never invented. The running operation is in memory. Preserve existing layouts, typed routes, pagination and auth/privacy semantics; adapt fields only where old queue claims would be untruthful. No profile-sync pending state is invented after removing that runtime.
- `getOnlineLapUploadStatus(accountId)` computes awaiting/rejected counts and latest matching receipt time from app DB rows. The worker supplies its single in-memory active operation and last error to the existing state endpoint. `OnlineSync` retains counts/status/time/error fields; unavailable counts are nullable unknown, not fabricated zero. A status-provider failure reports blocked/unavailable with unknown values, and the UI validator/presentation must accept that state without treating it as successful synchronization.


## 3. Lap finalization and one-time winner maintenance

### Finalization boundary

At finalization, the capture/lap owner derives attribution from **that lap's recorded packets**, using existing native parsers/evidence. It does so once for the completed lap, outside Online, without recording-history scans or replay-clock guesses. For imports, use the supported recorded provenance; missing evidence must not be invented.

Current code inserts/completes the row and then separately writes attribution in `server/telemetry/pipeline-ports.ts`. Change this boundary explicitly: final validity, recorded-packet attribution and the winner decision must be committed together under the existing write authority. Provisional rows are not final laps: leave their evaluated marker unset. Both a new completed insert and an update completing a retained provisional row must call the same finalization operation exactly once. Repeated publication must not compare an already-evaluated lap again.

### Minimal durable state

| Location / field | Meaning |
| --- | --- |
| `laps.online_evaluated_at` | Nullable timestamp; set once at completed-lap eligibility consideration. Includes invalid/non-Self/slower laps. Provisional rows remain null. |
| `laps.online_upload_result` | Nullable result code. Null means no terminal upload result; `success` means matching hosted receipt confirmed; other terminal values are sanitized hosted rejection codes. Null alone does not imply eligibility: the cron must join the current winner. |
| `laps.online_uploaded_at` | Nullable confirmation timestamp, retained where existing status consumers need it. Uploaded is derived from result `success`, not a second independent boolean. |
| Required transport identity | Stable original/request/idempotency identity and required receipt/reservation data on the lap only, as required by the installed API. No queue bookkeeping or duplicated attempt ledger. |
| Fastest-combo table | Unique native `(game_id, track_id, car_id)`, selected lap FK and selected integer lap time. This table is the authoritative set the upload cron visits. |
| `last_checked_lap_id` | Durable monotonic resume cursor in existing app-owned migration/state storage. Initialization scans `id > last_checked_lap_id ORDER BY id`; cursor advancement and considered-row/winner writes commit together. Not an upload queue. |

Use `lap_id REFERENCES laps(id) ON DELETE SET NULL`; null means no current winner and retained old time cannot block a future candidate. Do not invent fallback selection after deletion. Resolve exact existing SQL entity FK targets for game/car/track during the initial schema seam task, including whether discovered entities cover all supported IDs. Do not claim plain text keys are FKs. If extra canonical entities would be required, record the exact limitation and obtain approval rather than introducing a new catalogue implicitly. Keep tuple-to-lap consistency within schema/finalization transactions.

Approved schema seam (2026-10-23): existing `discovered_cars` and `discovered_tracks` are incomplete runtime metadata, and no canonical SQL game parent exists. Add minimal app-owned game identities and game-scoped native car/track identity tables, populated at capture/import boundaries and from existing session tuples during conversion. These tables represent identity only, not invented names or a new display catalogue. Winner game/car/track FKs target these identities. Persist a random installation identity outside portable recording metadata; only trusted live capture may attach it as recording origin. Historical rows without installation evidence remain unknown.

### Finalization transaction

1. Supply final recorded-packet attribution, validity, positive finite time and native combo; write the completed lap, whether inserting or completing its provisional row.
2. If already evaluated, preserve the decision. Otherwise mark evaluation once. Invalid, Other, Mixed, Unknown, imported or not-recorded-here laps do not compare against the winner and cannot upload. Imported Self/owned laps are excluded just like borrowed/community copies.
3. Only for an eligible valid Self lap recorded by this machine, execute one indexed conditional SQLite upsert: insert absent combo, replace null winner, or replace only when new time is strictly smaller. Ties retain existing winner. Store FK/time together. No separate comparison SELECT or application cache.
4. Commit final lap, attribution, evaluated marker and winner upsert atomically. Do **not** enqueue anything or set pending/uploading flags. The next upload cron observes the new winner directly.
5. Preserve the existing local dashboard/driver-summary metric update flow. Publication reflects committed lap data; failed/rolled-back finalization must not publish partial values. No new profile package, contribution preparation or profile transport is introduced.

Existing-data initialization runs once in bounded ascending lap-ID batches. Persist `last_checked_lap_id` with the evaluation/winner writes in the same transaction; restart reads only IDs greater than that committed cursor. Advance past invalid/non-Self/already-evaluated/deleted gaps as appropriate without repeating comparisons. Do not reset the cursor on restart or deletion. A failed transaction advances neither cursor nor evaluated state.

The cursor records ordered initialization progress, not a claim that every lower-ID row is finalized. A provisional row encountered by that scan keeps its evaluated marker unset and is later handled directly by its normal finalization operation, even when its ID is below the cursor. Concurrent live finalization must not jump the initialization cursor past unvisited older rows; its per-lap evaluated marker prevents a second comparison when initialization eventually reaches it. Repeated finalization checks that marker, not `id > cursor` alone. Persist ordinary one-time initialization completion so normal restarts do not restart the scan.

Reuse persisted attribution/recorded evidence through the capture owner; Online does not reconstruct it. After initialization, completed-lap finalization alone maintains winners. No cron population, unevaluated-lap poller, rule-version reset or source/binding-change reevaluation. Reprocessing preserves original evaluation identity; invalidating/deleting a winner clears it without historical fallback.

## 4. Sequential upload cron and outcomes

1. Use one supervised Online worker and existing scheduling. Each tick reads a bounded ordered set of current fastest-combo rows joined to laps with no terminal result, valid Self attribution, recorded-here non-import origin and allowed ownership/game/API prerequisites. No history enumeration or queue scan. Skip success, terminal rejection, every imported lap and mismatched/unknown recording origin.
2. Process laps **one at a time globally**, awaiting each attempt before the next. Cron ticks do not overlap: a tick while a pass runs does not start a second pass. This is a single worker operation, not a persisted lease/queue subsystem.
3. Just before request start, recheck current winner, valid Self attribution, recorded-by-this-machine non-import origin, usable source and current account/consent/sharing. A changed/ineligible winner is skipped; no historical alternative. Self, ownership, native file format or portable native-origin claims alone do not establish local recording eligibility.
4. Use the existing SDK/recording producer for the selected lap. Do not require removed Online readiness-recovery state merely to read a source: capture owns finalization/artifact availability. Unavailable/not-yet-readable source is skipped for this pass and may be tried by a later tick, without source repair or another winner evaluation.
5. Confirmed matching receipt: set that lap's result to `success`, store required remote identity and confirmation time. A hosted terminal rejection: store its rejection code. A rejection is not retried every tick. Success means request receipt, not anti-cheat approval or publication.
6. Offline/auth/policy/source unavailability and retryable network/429/503 failures are **not terminal rejection**. Leave terminal result null, respect the existing service retry/deadline rules and continue/finish the pass as appropriate. Use only minimal retry timing required by that protocol; do not create a scheduled-job table or retry queue. If one board is unavailable, it must not starve later rows indefinitely.
7. A lost response or restart uses the same persisted request identity as required by existing service idempotency. Transport acknowledgement lookup is allowed for that same request; it is not source/history reconciliation. Do not repeatedly upload an accepted lap under fresh identities.
8. If A starts and B then C become fastest, A may finish and records its own result only. Before the next request, consult current winner; B is not uploaded if already superseded, C is considered on the current/next pass. With global sequential execution, unrelated D waits its turn rather than uploading concurrently.
9. Deleting a lap clears its winner FK. A late response to a deleted row does not recreate it or update another row. No permanent local receipt history after row deletion is promised. Invalidation or attribution changing away from Self prevents a new transport without resetting evaluation. Never upload changed bytes under an old immutable request identity.

The winner table is maintained on lap finalization; the cron only handles upload. These are deliberately different execution paths.
