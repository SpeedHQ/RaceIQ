# RaceIQ Online backend implementation and product plan

ADR: [Decision record](../adr/0011-raceiq-live-service.md)
UI plan: [RaceIQ Online UI implementation](raceiq-online-ui.md)
Shared API contract: [RaceIQ Online UI/backend contract](raceiq-online-contract.md)

## Goal and ownership

RaceIQ is offline-first: every core feature works without an Online account, sign-in, or network. Discord sign-in is never required to install, onboard, record laps, review/analyze local data, or use the app. RaceIQ Online is optional cloud enrichment only—account-backed validation uploads and additional community leaderboards—not a prerequisite or replacement for offline features.

This plan owns backend implementation plus confirmed product requirements and end-to-end acceptance. “Backend” means local RaceIQ Bun/Hono routes and domain/storage modules plus an adapter to the external RaceIQ Online service; it does not mean implementing that external service. UI implementation is independently scoped in the [UI plan](raceiq-online-ui.md). The precise proposed local DTOs, routes, state rules, and ownership boundary are frozen in the [shared contract](raceiq-online-contract.md), which is authoritative for implementation. It is a proposed local API, not an existing or verified interface.

Backend and UI tracks can proceed in parallel. UI may build presentation against deterministic fixtures while backend work proceeds; full backend service readiness does not gate that work. Conversely, UI delivery is not a prerequisite for safe backend work. The backend's first shared prerequisite is implementation of the exact DTOs and shared export below plus typed Hono route composition; UI production RPC wiring waits for exported route types, not for auth, outbox, or live-service implementation. Unknown external-service/auth/sanitization gates block only operations that depend on them, not independent type, storage, route-boundary, fixture, or offline-isolation work. No production runtime stubs or fake success handlers.

## Confirmed product requirements

- Target published npm client `@speedhq/live-client@0.1.5`, whose contract has been inspected. Backend owns the workspace dependency upgrade; do not assume manifest/lockfile already select it. Earlier proposed GitHub Packages name is superseded by this verified public npm package; no registry credentials are required.
- Discord sign-in is optional. Online onboarding can be skipped; all local RaceIQ features remain available without Online account or network.
- Before first Online data transfer, require explicit acceptance of live-service Terms of Service and Privacy Notice. Persist consent version and acceptance timestamp according to server contract. Re-consent when required policy versions change. Consent gates only Online features, never offline RaceIQ.
- For users who choose Online during onboarding, present **Make my laps public**, enabled by default, with explicit choice. Users can change it later in minimal Online settings. Default-on draft is not effective until explicitly confirmed.
- Public participation controls whether lap data leaves the client. Private laps are never uploaded and receive no cloud validation. Only public laps qualify for upload, server validation, and public leaderboard eligibility. Turning public participation off stops new uploads; explain behavior before consent and beside setting.
- Setup inclusion is separate explicit opt-in, disabled by default. Public participation never implies setup consent. When off, omit optional setup attachment; when on, include only supported setup attachment authorized by that choice.
- For every supported F1 game, strip setup telemetry embedded in uploaded recording before submission, regardless of setup-attachment preference. Omitting optional setup file alone is insufficient. Preserve local recording and telemetry needed for lap validation; separately authorized setup attachment follows service's game-specific support.
- Upload user's fastest eligible public lap per track for live service. Deduplicate/retry safely. Upload only fields required by service contract, with F1 setup telemetry removed.
- First-release backlog: after sign-in, consent, and explicit public participation, scan locally stored eligible laps, select current fastest eligible lap per track, and enqueue for public submission/validation. Use durable, resumable, idempotent outbox and bounded background draining so rollout cannot create unbounded request burst. Never upload before consent or while private. If public participation turns off while work is queued, cancel or pause unsent work; do not drain validation uploads in private mode. Re-enabling recomputes eligible fastest laps rather than blindly replaying stale work.
- Fetch Online leaderboards into RaceIQ local client state/cache. Offline/local lap recording and analysis must not depend on successful Online requests.
- **Manage Account** opens `https://raceiq.snazzie.space/account` externally. Account administration—profile/identity changes, account deletion, and other controls—lives on website. RaceIQ exposes only Online connection state, sign-in/sign-out, public-lap and separate setup-inclusion preferences, and external link; do not build in-app account dashboard.
- Requested data scope: lap data, email, Discord ID, Discord name for live-service operation. No sale of PII; no unrelated third-party sharing. Since public leaderboard entries are visible to other users, Privacy Notice must explicitly disclose feature-specific visibility; do not claim lap data is never shared. Confirm exact stored fields, retention, deletion, and service processors against API/service policy before publishing claims.

## Backend scope and boundaries

### Backend owns

- External SDK dependency upgrade, adapter, Discord OAuth/callback and secure token lifecycle, policy/consent persistence, service preferences, account isolation, and sanitized error/status mapping.
- Exact shared DTO definitions and workspace export at proposed `shared/integrations/raceiq-online.ts`, following existing shared package export conventions. Use shapes/routes exactly as frozen in the [contract](raceiq-online-contract.md); coordinate any change with both plans and consumers. No inferred aliases, endpoint variants, units, enums, or defaults.
- Local Hono route modules and exported `AppType`, route validation/composition, transport protections, command state transitions, and backend enforcement independent of UI state.
- Race/privacy dispatch barrier: re-check current account, account epoch, policy versions/consent, effective confirmed public preference, and setup preference at each dispatch; sign-out/account switch/consent change/private mode prevent unsafe queued dispatch. Never trust UI disabling, enqueue intent, or stale DTO to authorize transfer.
- Fastest eligible lap selection, account-isolated durable outbox, bounded draining/backoff, idempotency as externally supported, F1 recording sanitization for backfill/new/retry, optional setup attachment control, validation/publication feedback, supported unpublishing, and leaderboard caching/mapping.
- Backend tests and runtime evidence for changed routes/domain behavior, plus root typecheck and final integration proof.

### File scopes and prerequisites

Existing route composition is `apps/backend/src/routes/index.ts` (Hono app exported as `app` and inferred RPC type); routers live in `apps/backend/src/routes/`. Keep new Online routes in that composition using existing route-module conventions. Runtime integration belongs in `apps/backend/src/runtime/`; reuse domain/storage boundaries under `server/` rather than inventing an `apps/backend/src/server/` tree. Inspect the closest existing domain/storage patterns during implementation. Shared types/export belong in `shared/integrations/raceiq-online.ts` and the existing shared export surface.

First backend contract deliverable: exact DTO types and export plus local route handlers/composition that establish route names and exported AppType for RPC consumers. Do not make success-shaped placeholder handlers: implement real behavior or return specified truthful unavailable/failure state. This unblocks UI production adapter typechecking. Backend can meanwhile implement independently safe domain/storage and external-adapter work; service-gated behavior must fail closed rather than claim service capability.

The UI owns onboarding/settings/Community Laps, localized copy, accessibility, React Query hooks, and Hono RPC adapter. UI implementation details and its acceptance are in [UI plan](raceiq-online-ui.md); do not duplicate its phases here. UI fixture scenarios can start before backend readiness, but fixtures remain test/preview-only and never become production fallback/auth simulation.

### Out of scope

- Requiring sign-in, network access, or live-service consent for any core or offline feature.
- Uploading private laps or providing cloud validation while public participation is off.
- Building separate RaceIQ account-management UI when external account page is required surface.
- Uploading full telemetry or additional identity data unless published service contract requires it and Privacy Notice is updated accordingly.
- Promising legal compliance or final legal terms without service-owner/legal review.
- Inventing external-service endpoints or claiming local routes imply external service support.

Production consumers can type against this surface without waiting for uploads.

Credentials are never stored in SQLite. Real login remains gated on Supabase provider setup and the exact loopback callback allowlist; remote callback exchange has not been verified.

This is not authenticated Online completion. The desktop OAuth/loopback callback flow is implemented locally, but real login remains gated on confirmation that the Supabase Discord provider and exact `raceiq_auth_nonce` loopback redirect are configured and allowlisted; no live exchange is claimed. The previous deployed probes reported policy metadata unavailable and an empty public-board catalog. Reviewed canonical identifier/eligibility production, service-compatible recording codec/F1 sanitizer, idempotency replay semantics, and account-bound withdrawal orchestration also remain gated. Local originals remain untouched; unverifiable F1 payloads fail closed.

Detailed runtime evidence and remaining integration gates are linked from `.omp/checkpoints/raceiq-online.md`. Local tests and typed route proof do not establish authenticated remote behavior. The shared DTOs, routes, units, defaults, and isolation contract remain unchanged.

## Backend implementation phases

1. **Shared contract and typed route prerequisite.** Implement exact DTOs/export in `shared/integrations/raceiq-online.ts` and shared workspace export. Add local route module(s) under `apps/backend/src/routes/`, compose in `apps/backend/src/routes/index.ts`, and ensure exported `AppType` matches contract's route mapping. Validate inputs and map errors to specified stable sanitized codes/statuses. This contract prerequisite is independent of full UI/backend delivery; no fake success handlers. UI production RPC adapter can type against this surface while fixtures remain usable.
2. **External adapter and account/consent boundary.** Use the workspace's exact public `@speedhq/live-client@0.1.8` dependency. Implement the adapter around `createRaceIqClient({ baseUrl })` and generated `api` operations (operations accept `{ client: apiClient }`), isolate external DTOs/errors, and resolve only verified operation behavior. Implement the documented Supabase desktop PKCE flow, callback handling, secure refresh-token lifecycle, policy-version consent, and confirmed preferences where supported. Gate account connection/transfer on authoritative current policies and explicit acceptance. Keep unresolved deployment availability and live-auth verification gates explicit; do not fabricate capability when unavailable. No upload/read requiring personal transfer before applicable consent.
3. **Preferences, account isolation, and barriers.** Persist effective public/setup choices only after successful confirmation. Private choice immediately installs local dispatch barrier and remains blocked on upstream-write failure; setup-off immediately suppresses attachments, even if upstream write fails. Public/setup enablement only takes effect after successful persistence. Account epochs/revisions and mutation serialization prevent stale commands, wrong-account queue use, late callbacks, or prior-account data hydration. Sign-out immediately blocks dispatch and clears local credentials/account-scoped state; external revocation failure does not lift barrier.
4. **Eligibility, sanitization, outbox, publication.** Determine fastest eligible public lap per track according to confirmed game/track/car and service semantics. On first confirmed public opt-in, scan persisted laps and enqueue current fastest eligible candidates. Use durable, resumable account-isolated queue, coalescing superseded work and bounded background draining with supported retry/rate-limit/idempotency behavior. Re-check barriers immediately before dispatch. Strip embedded F1 setup telemetry from recording bytes for historical backfill, new submissions, and retries without changing local original. Validate decoded outgoing recording has no embedded F1 setup telemetry and remains service/parser-valid; unsupported or unsafe sanitization fails closed with visible feedback, never unsanitized fallback. Attach setup only when separately enabled and supported; setup-off removes it from queued work/retries. Permanent validation failures pause/stop without retry loops. Turning public off cancels/pauses unsent uploads and invokes only supported withdrawal for already-public entries, reporting pending/failed/unavailable truthfully. Already-sent requests cannot be recalled.
5. **Leaderboard and account cleanup.** Map external game/track/car board identifiers to exact DTO rows, excluding email/Discord ID. Cache behavior/freshness follows confirmed contract; stale cached data must be marked accurately. Handle account deletion, queue purge, token invalidation, preference withdrawal, and migration/recovery only as service and storage behavior is established; website owns account administration. Online outage must not affect local data/capture.
6. **Verification and release integration.** Add backend route/domain tests for contract, auth/consent barriers, account isolation, preferences, queue/retry/idempotency, F1 sanitized output, unpublish, leaderboard/cache, and sanitized error mapping. Run root `bun run typecheck`, changed-backend runtime proof, and consumer-visible shared DTO/Hono RPC contract checks. Then integrate with UI production adapter and verify end-to-end privacy behavior and UI presentation separately. Update changelog/release notes once user-visible behavior is verified; all supported locales compile.

## End-to-end acceptance criteria

- Fresh install can skip Online setup and use all core features indefinitely without sign-in, Online credentials, or network access.
- No Online upload or personal-data transfer before explicit policy acceptance. Sign-in uses Discord via official client flow; credentials/secrets are not embedded in desktop client or committed.
- Onboarding initializes public participation enabled as a draft and obtains explicit user confirmation; user can turn it off later and see setting state.
- Private mode sends no lap recordings/setup attachments and performs no cloud validation, including signed-in users with accepted consent. Public mode submits eligible laps for server validation and potential public leaderboard publication; UI/privacy copy explains distinction.
- Setup inclusion defaults off and requires separate explicit choice. Public opt-in alone never sends setup attachment. Disabling setup inclusion omits attachments from subsequent dispatches, including queued work/retries.
- Every uploaded F1 recording has embedded setup telemetry stripped, even with setup inclusion enabled. Historical backfill, new submissions, retries use same sanitization boundary; local recordings remain unchanged. Outgoing decoded payload contains no embedded F1 setup telemetry and remains compatible with validation. Unsupported sanitization fails closed with user-visible feedback, never unsanitized fallback.
- Only fastest eligible lap per track is submitted; repeated syncs do not create duplicate entries; transient network failure does not lose local laps or break capture.
- First-release backlog backfill resumes after restart and does not duplicate server entries when retried; draining respects service limits and does not stall local recording/analysis.
- Turning public participation off with queued entries cancels/pauses unsent uploads; no validation-only requests continue. Re-check current preferences before each dispatch. Already-sent requests use supported unpublishing and truthful disclosure, not promise transmitted data can be recalled.
- Online leaderboard appears under Track Detail → Laps → Community Laps, not merged into local lap rows. Online outage leaves local and existing community content usable.
- Manage Account opens exact external URL in system browser. In-app Online controls limited to connection state, sign-in/sign-out, public-lap preference, separate setup-inclusion preference; profile/identity/account deletion controls stay on website.
- Privacy and Terms claims match actual API storage, visibility, retention, deletion, and third-party processing. PII is not sold; public lap display is disclosed.
- Turning public participation off also removes/unpublishes already-public entries where service supports it; disclose delayed/unavailable removal before consent and settings changes.
- Sign-out invalidates local tokens and prevents queued work from being sent under wrong account. Account deletion is managed externally and server/local queue effects are defined and tested.
- Queue survives restart, isolates work by account, coalesces superseded fastest-lap submissions, honors server retry/rate-limit responses, and stops/pauses on permanent validation rejection without retry loops.
- Public leaderboard identity fields are explicit and user-visible before publication; no email or Discord ID appears in leaderboard rows unless user is explicitly told and service policy requires it.
- Anti-cheat decisions are enforced by service, not trusted solely from client-supplied lap claims. Contract defines uploaded data, invalid-lap rejection, and RaceIQ feedback.
- Live-service eligibility is explicit for unsupported games, unknown tracks/layouts, and laps whose validity cannot be established; these never silently become public results.
- Shared DTO types/export, local routes and Hono AppType agree exactly with contract; production UI uses typed RPC rather than raw fetch or `any` casts. Fixtures prove presentation only, not backend enforcement.
- Supported locales compile; root typecheck and changed-backend runtime proof pass; final UI/backend integration exercises actual auth, policy, public submission, unpublishing, and leaderboard surfaces before claiming completion.

## Verified external contract and implementation gates

Contract investigation initially verified public npm artifacts `@speedhq/live-client@0.1.4` on 2026-10-10 and `@speedhq/live-client@0.1.5` on 2026-10-12. The workspace now pins the user-confirmed `@speedhq/live-client@0.1.8`; its published desktop-auth documentation and bundled contract are the implementation reference. Deployed compatibility must still be verified per operation rather than assumed from package version.

- Runtime client creation is `createRaceIqClient({ baseUrl })`; generated operations exported through `api` accept `{ client: apiClient }`. Earlier v0.1.4 `api.getPublicLeaderboards` request returned HTTP 200. Real v0.1.5 `api.getConsentPolicy` request returned HTTP 502 on 2026-10-12; current deployment and policy availability remain unverified.
- Authenticated operations require bearer token. Desktop sign-in is implemented with v0.1.8's documented `createDesktopAuth` and `raceIqAuthConfig` Supabase PKCE helpers; the loopback callback completes locally, access tokens remain in memory, and refresh tokens use OS-protected storage. Real Discord login, token exchange/refresh, provider configuration, and callback allowlisting remain externally unverified. Public Supabase configuration alone does not prove deployment readiness.
- The v0.1.8 bundled contract exposes `GET /api/v1/consent` and `GET`/`PUT /api/v1/me/consent`. Policy state includes availability, Terms/Privacy URLs and versions; acceptance records versions/timestamp. Authoritative policies and approved disclosures still require confirmation.
- `GET`/`PUT /api/v1/me/preferences` expose `visibility` (`public`/`private`) and `setupUploads`. Upload description says private laps/setups stay on client, public uploads require consent and public visibility, setup attachments require `setupUploads` opt-in. This matches clarified product behavior: private means no upload or cloud validation.
- `POST /api/v1/laps?gameId=...` accepts multipart required binary `recording` and optional binary `setup`, not lap-summary JSON or old raw octet-stream body. F1 embedded setup-telemetry stripping is a client requirement; inspected contract establishes no supported sanitization format. Confirm recording/parser compatibility before sanitized F1 upload.
- Upload operation documents optional `Idempotency-Key` header of 1–128 visible ASCII bytes. Replay, conflict, retention, and payload-change semantics need confirmation before promising duplicate-free retries.
- Owner lap listing exposes publication status and optional detector provenance (`complete`, `valid`, `invalidReason`, `lapIndex`, `uploadId`). `POST /api/v1/me/laps/{lapId}/unpublish` documents withdrawal from public competition. Confirm preference changes' effects on existing results and in-flight uploads; do not assume automatic bulk withdrawal.
- Public boards keyed by `gameId`, `trackId`, and `carId`. Confirm identifier mapping and fastest-per-track selection against per-car board model, canonical eligibility, and production processing availability.
- Earlier `/terms` and `/privacy` probes returned HTTP 404; current service/docs/privacy probes returned HTTP 502. Use policy endpoint authoritative URLs when available; do not assume fixed policy paths. Confirm retention, processors, deletion, optional setup sharing, and binary telemetry disclosures with service owner.

Earlier missing consent/preferences/unpublish/idempotency-header blockers are addressed in the published contract, and private validation is no longer a requirement. Remaining external gates: deployed compatibility and policy availability, approved disclosures, configured Supabase Discord provider and exact loopback callback allowlist, canonical eligibility/processing, safe F1 recording sanitization, and idempotency semantics. The local PKCE/callback and credential lifecycle are implemented, but live authentication/refresh remains unverified. Do not claim unresolved external behavior works. Never ship invented endpoints, unsanitized F1 uploads, automatic uploads while private or before consent, implicit setup sharing, or placeholder legal text. Core offline behavior remains unchanged.

## Unresolved contract decisions

- Workspace dependency selection is implemented at exact public npm client `@speedhq/live-client@0.1.8`; deployed operation compatibility remains gated separately.
- Confirm deployed Supabase Discord provider settings, public auth configuration, exact loopback callback allowlist, and live PKCE callback/refresh behavior.
- Exact meaning/payload of “fastest lap per track” across games, track variants, car classes, validity status.
- Exact public recording payload, safe F1 setup-telemetry stripping/parser compatibility, optional setup attachment support per game, leaderboard identity, preference enforcement, idempotency replay/conflict semantics, retention/deletion, and service-side processors.
- Whether leaderboard cache persists locally and its invalidation/freshness contract.
- Final Terms/Privacy text requires service-policy confirmation and legal review before release.
- Whether turning public participation off unpublishes existing leaderboard results, and how quickly removal takes effect.
- Public display name controls, identity fields exposed on leaderboard rows, and whether/how users can change display identity.
- Account deletion behavior, queued-data purge, and token invalidation across sign-out, account switch, and account deletion.
- Queue capacity/retention, coalescing when faster lap supersedes queued lap, permanent validation failures, account isolation, and behavior on HTTP 429/service outages.
- Fairness boundary: private laps stay local and receive no cloud validation; only public submissions undergo server validation. Setup attachments require independent opt-in; embedded F1 setup telemetry is always removed from uploaded recordings.
- Server-authoritative anti-cheat behavior and support for games/tracks/layouts where RaceIQ cannot provide trusted/canonical identifiers.
- Secure credential storage on supported platforms, OAuth callback/CSRF protections, TLS/service endpoint configuration in developer/CI environments.
- Whether service hosting or other processors receive data; reconcile facts with no-third-party-sharing statement before publishing Privacy Notice.
- Queue/database migration and recovery behavior for upgrades, uninstall/reinstall, local data deletion, and partial backfill.
