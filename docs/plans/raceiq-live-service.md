# RaceIQ Online backend implementation and product plan

ADR: [Decision record](../adr/0011-raceiq-live-service.md)
UI plan: [RaceIQ Online UI implementation](raceiq-online-ui.md)
Shared API contract: [RaceIQ Online UI/backend contract](raceiq-online-contract.md)

## Goal and ownership

RaceIQ is offline-first: every core feature works without an Online account, sign-in, or network. Discord sign-in is never required to install, onboard, record laps, review/analyze local data, or use the app. RaceIQ Online is optional cloud enrichment only—account-backed validation uploads and additional community leaderboards—not a prerequisite or replacement for offline features.

This plan owns backend implementation plus confirmed product requirements and end-to-end acceptance. “Backend” means local RaceIQ Bun/Hono routes and domain/storage modules plus an adapter to the external RaceIQ Online service; it does not mean implementing that external service. UI implementation is independently scoped in the [UI plan](raceiq-online-ui.md). The precise proposed local DTOs, routes, state rules, and ownership boundary are frozen in the [shared contract](raceiq-online-contract.md), which is authoritative for implementation. It is a proposed local API, not an existing or verified interface.

Backend and UI tracks can proceed in parallel. UI may build presentation against deterministic fixtures while backend work proceeds; full backend service readiness does not gate that work. Conversely, UI delivery is not a prerequisite for safe backend work. The backend's first shared prerequisite is implementation of the exact DTOs and shared export below plus typed Hono route composition; UI production RPC wiring waits for exported route types, not for auth, outbox, or live-service implementation. Unknown external-service/auth/sanitization gates block only operations that depend on them, not independent type, storage, route-boundary, fixture, or offline-isolation work. No production runtime stubs or fake success handlers.

## Confirmed product requirements

- Use the workspace's pinned public npm client `@speedhq/live-client@0.1.8`. Verify deployed upload and reservation behavior against that version; do not upgrade dependencies merely to connect the missing pipeline.
- Discord sign-in is optional. Online onboarding can be skipped; all local RaceIQ features remain available without Online account or network.
- Before first Online data transfer, require explicit acceptance of live-service Terms of Service and Privacy Notice. Persist consent version and acceptance timestamp according to server contract. Re-consent when required policy versions change. Consent gates only Online features, never offline RaceIQ.
- For users who choose Online during onboarding, present **Make my laps public**, enabled by default, with explicit choice. Users can change it later in minimal Online settings. Default-on draft is not effective until explicitly confirmed.
- Public participation controls whether lap data leaves the client. Private laps are never uploaded and receive no cloud validation. Only public laps qualify for upload, server validation, and public leaderboard eligibility. Turning public participation off stops new uploads; explain behavior before consent and beside setting.
- Setup inclusion is separate explicit opt-in, disabled by default. Public participation never implies setup consent. When off, omit optional setup attachment; when on, include only supported setup attachment authorized by that choice.
- For every supported F1 game, strip setup telemetry embedded in uploaded recording before submission, regardless of setup-attachment preference. Omitting optional setup file alone is insufficient. Preserve local recording and telemetry needed for lap validation; separately authorized setup attachment follows service's game-specific support.
- Upload user's fastest eligible public lap per track for live service. Deduplicate/retry safely. Upload only fields required by service contract, with F1 setup telemetry removed.
- First-release backlog: after sign-in, consent, and explicit public participation, scan locally stored eligible laps, select current fastest eligible lap per track, and enqueue for public submission/validation. Use durable, resumable, idempotent outbox and bounded background draining so rollout cannot create unbounded request burst. Never upload before consent or while private. If public participation turns off while work is queued, cancel or pause unsent work; do not drain validation uploads in private mode. Re-enabling recomputes eligible fastest laps rather than blindly replaying stale work.
- Fetch Online leaderboards into RaceIQ local client state/cache. Offline/local lap recording and analysis must not depend on successful Online requests.
- **Manage Account** opens `https://raceiq.snazzie.space/account` externally. Onboarding's name step shows the connected Online name as a placeholder; blank retains it, while a typed override updates the cloud `displayName` field and waits for confirmation before advancing. The retained or confirmed name is saved as local `driverName`. Any Discord-profile propagation is the cloud service's responsibility, not an app-side Discord mutation. Other profile/identity changes, account deletion, and administration remain on the website; do not build an in-app account dashboard.
- Requested data scope: lap data, email, Discord ID, Discord name for live-service operation. No sale of PII; no unrelated third-party sharing. Since public leaderboard entries are visible to other users, Privacy Notice must explicitly disclose feature-specific visibility; do not claim lap data is never shared. Confirm exact stored fields, retention, deletion, and service processors against API/service policy before publishing claims.

## Backend scope and boundaries

### Backend owns

- External SDK dependency upgrade, adapter, Discord OAuth/callback and secure token lifecycle, policy/consent persistence, service preferences, account isolation, and sanitized error/status mapping.
- Exact shared DTO definitions at `packages/online/src/contracts.ts`, exported through `@raceiq/online/contracts`. Use shapes/routes exactly as frozen in the [contract](raceiq-online-contract.md); coordinate any change with both plans and consumers. No inferred aliases, endpoint variants, units, enums, or defaults.
- Local Hono route modules and exported `AppType`, route validation/composition, transport protections, command state transitions, and backend enforcement independent of UI state.
- Race/privacy dispatch barrier: re-check current account, account epoch, policy versions/consent, effective confirmed public preference, and setup preference at each dispatch; sign-out/account switch/consent change/private mode prevent unsafe queued dispatch. Never trust UI disabling, enqueue intent, or stale DTO to authorize transfer.
- Fastest eligible lap selection, account-isolated durable outbox, bounded draining/backoff, idempotency as externally supported, F1 recording sanitization for backfill/new/retry, optional setup attachment control, validation/publication feedback, supported unpublishing, and leaderboard caching/mapping.
- Backend tests and runtime evidence for changed routes/domain behavior, plus root typecheck and final integration proof.

### File scopes and prerequisites

Existing route composition is `apps/backend/src/routes/index.ts` (Hono app exported as `app` and inferred RPC type); routers live in `apps/backend/src/routes/`. Keep Online routes in that composition using existing route-module conventions. Runtime lifecycle belongs in `apps/backend/src/runtime/`; `apps/backend/src/integrations/online.ts` composes the package service with host platform dependencies. Online domain/storage and browser-safe contracts belong in `packages/online/src`, exported through named `@raceiq/online/*` subpaths. The app-owned lap-candidate query remains in `server/db/online-upload-queries.ts`; do not create a package-to-backend dependency.

First backend contract deliverable: exact DTO types and export plus local route handlers/composition that establish route names and exported AppType for RPC consumers. Do not make success-shaped placeholder handlers: implement real behavior or return specified truthful unavailable/failure state. This unblocks UI production adapter typechecking. Backend can meanwhile implement independently safe domain/storage and external-adapter work; service-gated behavior must fail closed rather than claim service capability.

The UI owns onboarding/settings/Community Laps, localized copy, accessibility, React Query hooks, and Hono RPC adapter. UI implementation details and its acceptance are in [UI plan](raceiq-online-ui.md); do not duplicate its phases here. UI fixture scenarios can start before backend readiness, but fixtures remain test/preview-only and never become production fallback/auth simulation.

### Out of scope

- Requiring sign-in, network access, or live-service consent for any core or offline feature.
- Uploading private laps or providing cloud validation while public participation is off.
- Building separate RaceIQ account-management UI when external account page is required surface.
- Uploading full telemetry or additional identity data unless published service contract requires it and Privacy Notice is updated accordingly.
- Promising legal compliance or final legal terms without service-owner/legal review.
- Inventing external-service endpoints or claiming local routes imply external service support.

## Upload recovery implementation plan

### Scope and completion boundary

Connect the existing backend components so a signed-in user with current consent and confirmed public sharing automatically submits the fastest eligible local lap per game/track. Cover historical backfill, newly persisted laps, restart recovery, privacy restrictions, and truthful UI status. Keep local capture and analysis independent of Online failures. Reuse existing routes, storage, source readers, and typed RPC consumers; do not rebuild OAuth, account management, or Community Laps presentation.

This is a proposed implementation plan, not implementation approval or a claim that uploads work. The existing product requirements and end-to-end criteria below remain binding. The phases here are the execution order for the reported upload failure; the broader backend phases below retain background scope.

### Phase 1 — Verify the recording and service boundary

Owner: upload adapter/capture integration. Relevant scope: `packages/online/src/{adapter,payload,selection,identifiers}.ts`, `server/session-capture/source-loader.ts`, `packages/capture-formats/src/`, and the published client README/OpenAPI contract.

1. Establish an agent-runnable regression scenario: an already connected, consented, publicly sharing account with a real stored valid lap must reach the upload transport through the production orchestration path. Capture the current missing-dispatch failure before fixing it. Isolated auth/service fixtures may replace external dependencies, not the local selection/export/queue path.
2. Verify supported games (`acc`, `ac-evo`, `f1-2025`, `iracing`, `lmu`), canonical identifiers, local candidate rules, raw sparse `.bin` framing, parser versions, multipart limits, reservation response behavior, accepted-job reconciliation, and idempotency semantics. Forza remains unsupported by the published upload contract.
3. Resolve the current canonical eligibility proof gate. Derive candidate eligibility only from reviewed service rules and actual source metadata; do not invent proof IDs or an undocumented preflight endpoint. Local candidate checks are not server validation or anti-cheat approval. If the service requires a remote proof, verify how it is obtained before dispatch. Remove or replace a dead-end proof abstraction only after confirming the real contract.
4. Verify that lap-scoped recordings, including required pre-lap context and closing-boundary frames, are accepted by the service. Sparse deltas need a valid checkpoint; arbitrary byte slicing is not sufficient. Do not send an entire session merely because it contains the selected fastest lap.
5. Obtain compatible parser fixtures or service-parser access where the published client contract is insufficient. The README names raw sparse `.bin` but does not specify a complete codec/F1 sanitizer. Record the exact unresolved game/format requirement; independent storage/runtime work can proceed without treating that format as uploadable.

Exit gate: documented per-game payload/eligibility rules and a real capture accepted by the compatible parser. Production dispatch for any unverified format stays blocked; implementation cannot be declared complete with supported-game sanitization or compatibility unresolved.

### Phase 2 — Integrate the per-lap producer and sanitization (held)

Owner: the recording-strategy branch, followed by upload integration. The user has paused session extraction in this branch. Wait for the other branch's per-lap BIN publication and metadata contract; do not guess filenames, offsets, framing, or readiness signals.

1. Bind the upload preparer to the completed per-lap producer and verify exactly one logical lap against the authoritative service parser. Do not implement a parallel session slicer or send an entire session as fallback.
2. Implement the verified production codec for every supported format. Reject missing, truncated, unsupported, oversized, or identity-mismatched sources with an actionable error; do not substitute decoded summary JSON or fabricate telemetry.
3. Strip all embedded F1 setup telemetry, including setup content retained by sparse checkpoints/deltas, independent of optional setup-sharing preference. Preserve lap-validation channels and local original bytes.
4. Include optional supported setup attachments only under current explicit setup opt-in. Do not infer setup support from recording support.
5. Prepare an immutable upload payload or a reproducibly reconstructible payload with a stored content fingerprint. Bound memory and temporary storage; never load an entire large session merely to extract one lap. Remove prepared artifacts when no longer needed under defined terminal-job retention.

Exit gate: exported recordings recover the intended lap through compatible parsing, contain no unrelated session laps, and F1 output contains no embedded setup telemetry. Original raw/gzip sources are unchanged. Corrupt/missing sources fail without network transfer.

### Phase 3 — Complete durable queue identity and dispatch

Owner: outbox/service integration. Relevant scope: `packages/online/src/{outbox-storage,outbox,adapter,service}.ts` and package-owned outbox/adapter tests.

1. Add additive, versioned outbox migrations following its separate database convention. Persist a stable UUIDv7 idempotency key, payload fingerprint/reference, reservation token, remote job ID, and reconciliation state as required by the verified contract. Preserve existing terminal history; never edit released main-app migrations to change this separate DB.
2. Persist request identity before reservation and the reservation before upload. Resume interrupted reservation/dispatch only through documented idempotency or accepted-job reconciliation. If delivery cannot be established, retain truthful ambiguous state rather than blindly replaying or permanently blocking a track without an actionable explanation.
3. Separate durable account ownership from process-local authorization epochs. `createRaceIqOnlineService()` currently rotates the epoch at startup: pending work must resume only after current credentials, account, consent, and preferences are confirmed for the same owner. Never authorize another account's jobs or revive work withdrawn by a privacy restriction.
4. Preserve fastest-per-game/track coalescing, terminal-history deduplication, queue caps, bounded draining, bounded attempts, and server rate-limit/backoff behavior. Revalidate candidates after source deletion/reprocessing or a faster replacement. Do not use per-car selection unless product requirements are explicitly changed.
5. Serialize each transport start with restrictive service mutations. Recheck account/token alignment, current policy consent, confirmed public visibility, and setup preference immediately before both reservation and binary submission. Private mode, sign-out, account switch, or required re-consent prevents all new sends. Do not hold a long network request across local privacy-barrier installation.
6. If prepared bytes change, including removal of an optional setup attachment, retire the unsent request identity and create a new one; never reuse an idempotency key for changed content. Already-sent requests require reconciliation, not payload replacement.

Exit gate: restart resumes authorized pending jobs, private/account-switch races send no new bytes, faster laps supersede pending slower work, and interrupted/duplicate requests reconcile without duplicate remote jobs. Ambiguous and permanent failures remain visible.

### Phase 4 — Connect runtime triggers and truthful sync status

Integration owner: backend runtime/service. Relevant scope: `apps/backend/src/runtime/{boot,startup-jobs,shutdown}.ts`, `server/telemetry/{live-pipeline,pipeline-ports}.ts`, lap-import/reprocessing completion seams, Online service/routes, and current client Online hooks/settings.

1. Start one bounded, single-flight upload coordinator after DB/runtime initialization. Schedule paged historical scans when a restored account becomes authorized, consent/public opt-in is confirmed, and public participation is re-enabled. Recompute current fastest candidates rather than resurrecting withdrawn queue entries.
2. Notify the coordinator after durable lap save/import/reprocessing completion and readable source publication. A live lap can be saved while the capture is still open; defer until the required bytes are available without blocking telemetry. Coalesce notifications and avoid repeated full-history scans on state polling. Preserve provenance/deduplication when importing an already-public cloud lap.
3. Drain automatically while authorized, waking on due retry time, source readiness, or state changes. Stop timers/new dispatch on shutdown; leave pending jobs durable and classify interrupted transport truthfully.
4. Replace fixed sync counts with account-scoped queue/runtime state. Populate queued/in-flight/rejected counts, last error, and last successful transfer timestamp from durable outcomes. `idle` means no pending/running work; preparation or capability failures must not appear as successful idle sync. Do not equate `uploadAllowed` with a completed upload.
   - Add a persistent **Upload queue** status panel in General settings' Online section, using the existing `OnlineSection.tsx` surface without adding another settings destination. Show a textual state (checking, idle, uploading, paused, blocked, or status unavailable), queued/uploading/rejected counts, **Last synced** time when known, and the current block reason/latest error. Bind Last synced to `sync.lastSyncedAt`: the most recent confirmed successful upload, not the last poll, scan, or attempted transfer. Show "Never synced" when no successful upload is recorded, and expose the exact localized date/time alongside any relative display.
   - Keep the panel visible when the queue is empty or uploads are blocked, rather than rendering only running/error notices. Distinguish "No uploads queued" from "All laps uploaded": zero queued work does not prove successful selection, export, or submission. Distinguish upload status from remote validation/publication.
   - Derive every value from account-scoped backend state. While loading or unreachable, show checking/unavailable instead of fabricated zeros; mark cached values stale and hide previous-account values immediately on sign-out/account switch. Reuse existing refresh/retry behavior without introducing an unsafe force-upload action.
   - Preserve incumbent layout and accessible status semantics; state must not depend on color alone. Add localized copy in every supported locale. Verify desktop/mobile layouts, empty, active, paused/blocked, rejected, and unreachable/stale states. UI ownership and acceptance are also recorded in the [Online UI plan](raceiq-online-ui.md#settings-dedicated-online-section).
5. Track remote queued/processing/validated/rejected publication outcomes through documented job/owner-lap APIs. HTTP acceptance proves transfer, not validation or leaderboard publication. Reuse existing UI contract fields where sufficient; if additional states/errors are necessary, update shared DTOs, contract document, Hono RPC consumers, and every supported locale together.
6. Connect existing restrictive preference handling to unsent withdrawal and supported account-bound unpublishing. Already transmitted data cannot be recalled locally; show pending/failed/unavailable withdrawal truthfully. Do not expand this work into website account administration.

Exit gate: existing public users get automatic historical uploads without another sign-in; a newly recorded faster lap uploads without manual intervention; restarts resume; General settings' Online section has a persistent Upload queue panel showing actual activity, counts, block reasons, Last synced time, and errors rather than fixed zeros or a false completion claim. Last synced survives restart, changes only after confirmed successful upload, and cannot leak another account's timestamp. Private/offline users continue recording normally.

Exercise actual runtime backfill, new-lap submission, faster replacement, restart, private-mode switch during preparation/dispatch, setup-off, account switch, changed policy, 429/backoff, interrupted reservation/upload, missing/corrupt capture, service validation rejection, and unsupported game handling.

Remove temporary harnesses, payload artifacts, and debug instrumentation. Record precisely any external gate that remains unverified; do not label uploads complete.

## End-to-end acceptance criteria

- Fresh install can skip Online setup and use all core features indefinitely without sign-in, Online credentials, or network access.
- No Online upload or personal-data transfer before explicit policy acceptance. Sign-in uses Discord via official client flow; credentials/secrets are not embedded in desktop client or committed.
- Onboarding initializes public participation enabled as a draft and obtains explicit user confirmation; user can turn it off later and see setting state.
- Private mode sends no lap recordings/setup attachments and performs no cloud validation, including signed-in users with accepted consent. Public mode submits eligible laps for server validation and potential public leaderboard publication; UI/privacy copy explains distinction.
- Setup inclusion defaults off and requires separate explicit choice. Public opt-in alone never sends setup attachment. Disabling setup inclusion omits attachments from subsequent dispatches, including queued work/retries.
- Every uploaded F1 recording has embedded setup telemetry stripped, even with setup inclusion enabled. Historical backfill, new submissions, retries use same sanitization boundary; local recordings remain unchanged. Outgoing decoded payload contains no embedded F1 setup telemetry and remains compatible with validation. Unsupported sanitization fails closed with user-visible feedback, never unsanitized fallback.
- Only fastest eligible lap per track is submitted; repeated syncs do not create duplicate entries; transient network failure does not lose local laps or break capture.
- First-release backlog backfill resumes after restart and does not duplicate server entries when retried; draining respects service limits and does not stall local recording/analysis.
- Turning public participation off with queued entries cancels/pauses unsent uploads; no validation-only requests continue. Re-check current preferences before each dispatch. Already-sent requests use supported unpublishing and truthful disclosure, not promise transmitted data can be recalled.
- Online leaderboard appears under Track Detail → Laps → Community Laps, not merged into local lap rows. Online outage leaves local and existing community content usable.
- Manage Account opens the exact external URL in the system browser. The onboarding name step starts empty with the connected account's display name as placeholder. Blank retains that name without a profile mutation; overrides are confirmed by Online before advancing and used locally. Failures remain actionable without claiming success. Offline names stay local-only. Other profile/identity/account deletion controls stay on the website.
- Privacy and Terms claims match actual API storage, visibility, retention, deletion, and third-party processing. PII is not sold; public lap display is disclosed.
- Turning public participation off also removes/unpublishes already-public entries where service supports it; disclose delayed/unavailable removal before consent and settings changes.
- Sign-out invalidates local tokens and prevents queued work from being sent under wrong account. Account deletion is managed externally and server/local queue effects are defined and tested.
- Queue survives restart, isolates work by account, coalesces superseded fastest-lap submissions, honors server retry/rate-limit responses, and stops/pauses on permanent validation rejection without retry loops.
- Public leaderboard identity fields are explicit and user-visible before publication; no email or Discord ID appears in leaderboard rows unless user is explicitly told and service policy requires it.
- Anti-cheat decisions are enforced by service, not trusted solely from client-supplied lap claims. Contract defines uploaded data, invalid-lap rejection, and RaceIQ feedback.
- Live-service eligibility is explicit for unsupported games, unknown tracks/layouts, and laps whose validity cannot be established; these never silently become public results.
- Shared DTO types/export, local routes and Hono AppType agree exactly with contract; production UI uses typed RPC rather than raw fetch or `any` casts. Fixtures prove presentation only, not backend enforcement.
- Supported locales compile; root typecheck and changed-backend runtime proof pass; final UI/backend integration exercises actual auth, policy, public submission, unpublishing, and leaderboard surfaces before claiming completion.
