# Diagnostic export

RaceIQ produces `raceiq-diagnostics.zip` from **Settings → Diagnostics**. The
archive is intended for support and engineering investigation. Treat it as
sensitive: it can contain AI prompts, conversations, responses, stack traces,
local paths, and system details.

## Archive contents

| File | Contents |
| --- | --- |
| `diagnostics.json` | App, browser, operating-system, hardware, network, server, database, telemetry, AI configuration, and chat summary fields |
| `logs.txt` | Retained server/client logs plus exported AI conversation context |

The export is generated by `GET /api/diagnostics` in
`server/routes/system/diagnostics-routes.ts`.

## Log retention and volume

Server logs use the following policy:

- active file: `<DATA_DIR>/raceiq.log`;
- rotation threshold: 2 MiB;
- rotated-file retention: 25 hours by file modification time;
- restart markers are written into the log;
- export order is oldest eligible rotated file first, active file last;
- files older than the retention cutoff are excluded and pruned;
- there is no total retained-byte or file-count cap;
- one log entry can exceed the 2 MiB rotation threshold.

This guarantees time-based retention, not a strict maximum archive size. Heavy
logging can produce many files during the 25-hour window.

AI conversation context is appended after retained files and is not governed by
the 2 MiB rotation threshold. Current chat-memory configuration recalls at most
50 messages per thread, so the export does not yet guarantee complete history
for longer threads.

## Diagnostic fields

`diagnostics.json` currently includes:

- app version, compiled state, install/data directories, drive type, and Bun version;
- browser name, version, engine, user agent, and browser heap use when exposed by Chromium;
- OS name, platform, architecture, release, uptime, CPU model/count/use, GPU
  name/use, memory, network type/link speed, and power mode;
- UDP port/activity/rate/drop count, WebSocket client count, server heap use,
  database size/counts, detected game, and current session identifiers;
- effective telemetry and AI provider/model settings;
- chat thread IDs, update values, message counts, latest retained AI error, and separate chat-context collection error;
- archive generation time.

Unsupported or failed hardware probes currently appear as `null` or `Unknown`.
The archive does not distinguish unsupported platform, missing command,
permission failure, malformed output, or probe timeout.

## Hardware detection limitations

Stable cross-platform fields use Node OS APIs: OS, architecture, release, CPU
model/count, total/free memory, and uptime.

CPU utilization, GPU identity/utilization, link speed, power mode, and drive
media type currently have Windows-specific PowerShell implementations. macOS
and Linux exports leave most of these fields empty.

Known limitations:

- network selection uses the first non-internal IPv4 interface and guesses its
  type from its name; VPN, tunnel, bridge, virtual, Wi-Fi, and secondary
  adapters can be misclassified;
- Windows network selection can report an adapter different from the default-route adapter;
- Windows CPU load uses the first parsed processor value rather than an aggregate on multi-socket systems;
- Windows GPU selection and utilization collapse multi-GPU systems into one
  name/value and can select or aggregate the wrong adapter;
- Windows drive detection calls `Get-PhysicalDisk -DeviceNumber`, which is not
  a documented parameter and can produce `Unknown`;
- synchronous PowerShell probes have no explicit timeout and discard command
  exit/error details.

An isolated host comparison confirmed CPU model/count, memory, OS, and
architecture, but misclassified an active Wi-Fi default route as Ethernet and
omitted an available GPU. Windows behavior still requires validation on a
representative Windows system.

## AI provider errors

Structured diagnostics cover Gemini, OpenAI, OpenAI-compatible, Claude CLI,
agent-stream, and lap-analysis request paths. Provider transport failures,
malformed JSON, empty responses, non-success HTTP responses, and lap-analysis
generation or output-validation failures are written as error-severity
`llm-error` events and appear in `logs.txt` when the configured log level
includes errors.

Current limitations:

- local OpenAI-compatible auto-tune calls bypass shared provider diagnostics;
- failures before agent stream creation and some response-persistence failures
  lack complete provider/model/thread context;
- provider errors lack consistent duration, correlation ID, HTTP status,
  retryability, attempt, and feature metadata;
- upstream error bodies and some provider console messages need stronger
  credential and sensitive-content scrubbing.

## Browser and client errors

Client startup installs capture before loading release features and mounting
React. It forwards:

- uncaught `window` errors;
- unhandled promise rejections;
- `console.debug`, `console.info`, `console.warn`, and `console.error` calls;
- heap-pressure and prior unexpected-session breadcrumbs emitted through those paths.

Records are coalesced for 500 ms and posted to `POST /api/client-log`. The server
preserves client occurrence time, scope, detail, message, and severity in its
structured log. Successfully delivered records therefore appear in
`logs.txt`.

Client-side bounds prevent recursive/noisy failures from exhausting resources:

- 32 coalescing entries;
- 32 queued entries;
- 2 concurrent requests;
- 4,000-character messages;
- 4 KiB serialized detail budget, reduced to a 1 KiB preview when truncated.

Delivery is best-effort. Transient network failure, offline state, queue
overflow, navigation, tab termination, or downloading diagnostics during the
500 ms coalescing window can lose records. The export does not flush pending
client reports or report drop counts before download.

## Privacy and security boundary

The archive can include raw AI requests, responses, system prompts, persisted
chat messages, upstream error bodies, URLs, stack traces, and local paths.
Current normalization redacts selected credential-shaped object keys, but it is
not a comprehensive content scrubber. Users should inspect the archive before
sharing it outside trusted support channels.

Recommended hardening:

1. remove credential-bearing URLs and unsanitized upstream bodies from logs;
2. apply one recursive sanitizer to structured logs and exported chat data;
3. make full conversation export an explicit, clearly labelled choice;
4. include truncation and dropped-event metadata in the archive.

## Useful additions

Highest-value additions for support investigations:

1. log coverage start/end, retained bytes/file count, configured level, and
   dropped/coalesced client-event counts;
2. complete-chat or explicit truncation metadata with bounded export size;
3. process RSS, database WAL/SHM sizes, filesystem free space, and disk health;
4. default-route adapter identity, type, address family, link speed, and probe status;
5. per-GPU identity/utilization or explicit unsupported status;
6. structured hardware probe status and bounded execution time;
7. AI request correlation IDs, feature/route, duration, status, retryability,
   attempts, and token usage without credentials;
8. relevant feature flags and sanitized effective runtime configuration.

## Verification record

An isolated end-to-end export exercised the real route and archive parser. It
confirmed:

- a 24-hour-old rotated log is included;
- a 26-hour-old rotated log is excluded;
- forwarded browser errors appear in `logs.txt`;
- Gemini and OpenAI transport failures appear in `logs.txt` at the default log level;
- those AI failures remain present when the minimum level is `warn` because failure events use `ERROR` severity;
- 60 persisted messages produce 50 exported chat-message records;
- the ZIP contains valid `diagnostics.json` and `logs.txt` entries.

Focused tests:

```sh
bun test ./client/test/report-error.test.ts
bun test test/routes/diagnostics-routes.test.ts test/runtime/diagnostic-log-store.test.ts test/ai/diagnostic-logging.test.ts
```
