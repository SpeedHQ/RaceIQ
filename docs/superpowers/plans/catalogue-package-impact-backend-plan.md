# Catalogue package impact: backend plan

Status: proposed. [Shared contract](catalogue-package-impact-contract.md) · [UI plan](catalogue-package-impact-ui-plan.md) · [ADR 0017](../../adr/0017-catalogue-package-impact.md)

## BE-01: Isolate catalogue-facing backend dependencies

**Owner and scope.** Backend implementation owner starts with `packages/{cars,tracks}-catalogue/server/**`, `apps/backend/src/routes/index.ts`, `apps/backend/src/tracks/corner-resolution.ts` and the query/registry modules named below. Integration owns manifests, lockfile and Turbo tasks. Agree exact extraction files and package names at the first checkpoint below before moving shared code. No recorder refactor, schema changes, new DB instance, endpoint changes or migration of unrelated backend-core consumers. Start after contract approval; no UI implementation dependency.

1. Use `bunx --no-install turbo run e2e:impact --dry=json` and the feature import boundary checker to verify the current closure. Both catalogue tasks reached `server/session-capture/direct-recorder.ts` through `@raceiq/backend-core#transit` on #542. Confirm which links are only package-wide and which are real. Start with Cars `car-routes.ts`: discovered-car queries, `tryGetServerGame`, and data paths. Tracks also consumes discovered-track queries, lap counts and reads, geometry and segments, calibration, guide and recorded-lap paths. `server/db/lap-read-queries.ts` mixes `getLapCountsByTrack` with capture-backed reads; do not treat the entire module as a simple catalogue query. Trace the existing corner-resolution caller as well as the Hono mount.
2. **Extraction checkpoint.** Identify existing narrow owners for game paths and metadata, then present the exact file/caller list for the smallest missing capability. Keep catalogue-only policy in its current feature. For shared query code, prefer an existing neutral owner; introduce one purpose-named workspace only where multiple consumers need it. A shared package may accept the app-owned DB executor or registry interface but must not import `@raceiq/backend-core` back through that interface. Use existing DB/schema/types as the authority; if extracting a query would require moving the DB lifecycle or schema, stop and request scope approval. Reject a new package that brings `backend-core#transit` back transitively.
3. Migrate Cars first and replace the broad dependency only after all real imports move or are wired through existing typed boundaries. For Tracks, separate count/discovery reads from recorded-lap/detail reads at their actual consumers. Keep any verified recorded-lap or capture-ready edge. Do not add an exemption for #542 or drop `backend-core` while Tracks still imports it. If removing the broad edge for Tracks requires recorder moves or a separate detail suite, stop and bring that tradeoff to the user, preserving current Tracks coverage. Preserve mount order and route typing through `apps/backend/src/routes/index.ts`; validate impacted tests/callers when query or router exports move.

**Acceptance and handoff.** [CAT-2/E2, CAT-3/E3 and CAT-4/E4](catalogue-package-impact-contract.md#acceptance-and-end-to-end-evidence) cover owned APIs, recorder/discovery/lap reads, and shared runtime/schema changes. CAT-5/E5 covers missing ownership and full mode; CAT-6/E6 covers real query/API/UI integration. Report the before/after task graph, verified detail edges and any blocked extraction to integration. Integration runs the shared selector, hosted and compiled-app scenarios, including Tracks import/delete and capture readiness; do not claim a skipped suite from static inspection.

## Extraction checkpoint: Cars host

No new workspace or shared server file move is needed for Cars. `packages/cars-catalogue/server/car-routes.ts` owns a typed router factory; `apps/backend/src/routes/catalogue-cars.ts` supplies the existing discovered-car reads, game registry and configuration path. The app router and its two integration consumers (`apps/backend/test/routes/car-routes-game-id.test.ts` and `packages/sessions-page/test/integration/session-identity-repair.test.ts`) share that same app binding. The package declares the existing backend implementation inputs for this seam without a full `backend-core` transit edge.

Tracks now imports lap counts from `server/db/track-queries.ts`, not the recorded-lap module. Keep the Tracks backend-core dependency: `tracks.spec.ts` covers the import/delete path and capture-ready event, and the real import pipeline depends on `DirectSessionRecorderAdapter`. Splitting that coverage into a different suite or moving the recorder is outside this plan.
