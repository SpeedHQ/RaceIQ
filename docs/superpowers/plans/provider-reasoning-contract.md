# Provider reasoning contract

Plans: [UI](provider-reasoning-ui-plan.md) and [backend](provider-reasoning-backend-plan.md). Status: draft for review, not implementation authorization.

## Scope and existing behavior

Extend reasoning controls in AI Analysis (lap and comparison) and AI Chat (lap, comparison and setup). Setup chat consumes AI Chat preferences; it does not gain a separate setting. Auto-tune and Driver Profile are unchanged, including on shared transport paths. Leave OpenAI model discovery and the `Medium ⭐` label alone. Preserve the [OpenAI contract](openai-reasoning-contract.md) and existing Gemini thinking budgets. Use the shared `SearchSelect` for the reasoning choices.

## Settings and capabilities

Keep `GET /api/settings` and `PUT /api/settings`, their existing authentication, and response/error conventions. Extend `server/runtime/config/settings.ts` with the optional storage fields `aiProviderReasoning` and `chatProviderReasoning`. GET always exposes both as objects, defaulting to `{}`. Each object is a sparse map keyed by `gemini`, `anthropic`, `deepseek`, or `openai-compatible`; official OpenAI continues using `aiReasoningLevel` and `chatReasoningLevel` exactly as documented in the existing contract.

A map entry is a string: `default`, `off`, `minimal`, `low`, `medium`, `high`, `xhigh`, or `max`. An absent key and `default` both mean use the existing behavior for that provider and workflow. PUT accepts either optional, non-null map and merges entries by key, leaving omitted fields and keys unchanged. Example: `{ "chatProviderReasoning": { "deepseek": "high" } }` updates only DeepSeek chat. Use `default` to reset a key. Unknown keys, non-enum strings, nulls and invalid types reject the entire PUT with the existing 400 response. Schema validation does not reject a valid preference just because it is not available on today's active model: a saved preference must survive switching models and providers. Old settings files require no migration for the new maps; existing OpenAI migration and Gemini budget fields are unchanged.

Use one shared capability resolver for UI and backend. Input: provider, effective model ID (including the runtime default if no model is selected), and configured endpoint where applicable. Output: unavailable, existing Gemini token-budget mode, or an ordered set of named choices and their provider-specific semantics. Match only documented model families and endpoint protocols supported by the installed SDK or current adapter; unknown models and custom gateways default to unavailable for named choices. Do not infer gateway support from OpenAI-shaped URLs, IDs, or `/models` responses without explicit capability information. Keep the actual model/protocol mapping in the shared resolver; backend adapters serialize the result. Before implementation, record supported model families, exact choices and wire values against provider docs and the installed adapter version. At minimum, cover a verified named-level model for Gemini and Anthropic, and a verified thinking-control model for DeepSeek. An arbitrary gateway without verified support gets no selector; do not add a probing service or new opt-in setting.

- **OpenAI:** Preserve the existing selector and request/error behavior.
- **Gemini:** Show named levels only on models with a verified named-level API. Preserve the existing numeric budget UI and saved values on budget-mode models. Do not send named levels and token budgets together; provider default in named mode omits the explicit level.
- **Anthropic:** Use only the thinking/effort combinations accepted by the verified model and transport. Never translate `off` to a low effort or expose `off` when unsupported.
- **DeepSeek:** Send a named effort or thinking toggle only where the model and transport support it. `default` preserves existing behavior per path, including disabled thinking on the raw structured path. Explicit reasoning must preserve tool calls and usable final output. Do not silently retry with thinking disabled after truncation.
- **OpenAI-compatible:** Send no new reasoning fields unless the exact endpoint/model capability is verified. Preserve existing transport behavior in the absence of support.

A stored level unavailable on the current model displays Default; keep the stored preference intact and apply it again when supported. Do not overwrite it on unrelated saves. For non-default supported choices, if the SDK drops the setting or the upstream rejects it, explain how to change the level in Settings and retry. Do not mark the generation successful, save an analysis, or finalize a chat reply without the explicitly requested level. Keep the existing error path for unrelated failures. A failed settings save is visible and does not update persisted preferences.
