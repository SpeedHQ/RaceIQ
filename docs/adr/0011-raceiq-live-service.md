# Keep RaceIQ Online optional and offline-first

RaceIQ is offline-first: all core features work without an Online account, sign-in, or network. Discord sign-in is never required to install, onboard, record laps, or use local review and analysis. RaceIQ Online is optional cloud enrichment for account-backed validation of public lap submissions and additional community leaderboards, not a prerequisite or replacement for offline features. Place Online standings in Track Detail → Laps → Community Laps. Keep RaceIQ Online controls minimal: connection state, Discord sign-in/sign-out, public-lap and separate setup-inclusion preferences, onboarding synchronization of the public leaderboard display name, and an external Manage Account link. Other profile and account administration stay on the Online website. Display-name synchronization uses the verified `PATCH /api/v1/me` profile contract in `@speedhq/live-client@0.1.8`.

Separate UI implementation from backend implementation so both tracks can proceed in parallel against one explicit boundary: backend owns shared DTOs/export, typed local Hono routes, external-service adapter, auth/consent/preferences, privacy and dispatch barriers, queue, sanitization, and leaderboard mapping; UI owns presentation, localized copy, and typed RPC consumer. Local backend means RaceIQ's Bun/Hono server plus an adapter, not a redesign or presumed capability of the external service. The [shared contract](../plans/raceiq-online-contract.md) is the proposed local API baseline, not an already implemented interface. This division preserves clear enforcement ownership without blocking UI fixture work or safe backend work on unresolved service gates.

Public participation defaults on only as an explicit-confirmation draft; private laps remain local and receive no cloud validation. Setup attachments require a separate default-off opt-in; public participation never implies setup sharing. Embedded F1 setup telemetry is stripped from every uploaded recording regardless of attachment preference, while local source recordings remain unchanged. Initial public opt-in backfills eligible fastest laps through a durable, resumable account-isolated queue with bounded background draining. Backend rechecks consent, account, and effective preferences at dispatch and fails closed when service behavior or sanitization is unresolved. External API policy availability, desktop auth, eligibility, idempotency, and sanitization compatibility remain gates to the operations depending on them; they do not block independent typed routes, safe storage/domain work, or UI fixtures. Never invent endpoints or present proposed local routes as external service capabilities.

## Upload recovery execution decision

Connect the existing capture, candidate selection, durable outbox, and adapter through one bounded backend coordinator; do not rewrite working sign-in to address missing dispatch. Backfill after authorization and notify after durable lap/source publication. Export only the selected lap with parser-required sparse context, not an entire session, and verify service compatibility before enabling that format. Local candidacy is not service validation; do not fabricate canonical proofs to satisfy the current eligibility gate.

Persist immutable request identity, reservation/job reconciliation data, and durable account ownership separately from process-local authorization epochs. Serialize transport starts with privacy restrictions, resume only under confirmed current authorization, and expose actual queue and service outcomes instead of fixed zero counts. Transfer acceptance is not validated publication. This avoids unsafe session over-sharing, duplicate submissions, and stale-account dispatch while preserving offline recording. The [upload recovery implementation plan](../plans/raceiq-live-service.md#upload-recovery-implementation-plan) defines phases and verification gates. This decision remains proposed.

General settings' existing Online section will expose a persistent Upload queue panel with account-scoped activity, counts, blocking reason, latest error, and **Last synced** time from `sync.lastSyncedAt`. That timestamp records the most recent confirmed successful upload, not polling or an attempted transfer, and survives restart without leaking across accounts. Empty queues are not proof that every lap uploaded; loading/stale/unreachable states must not imply success, and transfer status remains separate from service validation/publication. Reuse the incumbent settings destination and shared sync contract where sufficient.
